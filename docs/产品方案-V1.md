# 县域家居水电运维平台｜产品方案 V1.3

> 产品定位：面向县域散户、物业与企业客户，以“服务电商 + 可信履约 + 企业维保项目”为核心，连接服务搜索、分类选购、购物车、多诉求下单、批量工单、派单、施工留证、材料溯源、结算、质保与对账的数字化经营系统。

**方案状态：** 创始人讨论稿  
**产品范围：** 微信小程序（客户端 + 师傅工作台）+ Web 中后台  
**输入依据：** `docs/合伙人输入` 全部材料  
**建议首发策略：** 一期以物业/企业维保项目为经营主线，按“约 10 万元级企业维修/维保项目”设计首个标杆交付；同时上线具备分类、搜索、购物车和多诉求合单能力的 C 端服务商城。若“10 万单”实际指 10 万张工单，而不是 10 万元级项目，需另行提高容量与组织方案。

**V1.3 导航与目录决策：** C 端底部导航固定为“首页、全部服务、我的”三项。购物车仍保留多诉求合单能力，但作为低频交易工具，只从服务详情、首页角标和“我的”中的订单/购物入口进入，不占用 TabBar。服务分类必须由管理后台统一维护，SKU 新建/编辑只能选择后台启用分类；小程序首页和“全部服务”均读取同一分类目录。

## 1. 产品结论

### 1.1 一句话产品

让客户敢下单、让公司管得住、让师傅干得清、让每次施工有证据、让一次上门持续产生后续价值。

### 1.2 产品本质

项目不是撮合平台，但客户侧应参考成熟电商平台的选购逻辑。前台是可搜索、可分类、可加入购物车的“服务电商”，后台是一套自营服务公司的数字化操作系统：

1. **前台服务电商：** 客户通过搜索和分类找到多个服务 SKU，加入购物车，合并提交多项维修诉求，再完成预约、支付、查进度、验收与售后。
2. **履约控制系统：** 派单、签到、勘察、报价、开工、影像留证、材料领用、验收、质保。
3. **经营闭环系统：** 客户档案、服务资产档案、复购提醒、优惠权益、转化线索、经营数据。
4. **B 端项目履约系统：** 物业/企业项目、合同、服务点位、批量报修、工单、SLA、额度、对账与回款。

### 1.3 为什么值得自建

成熟家政 SaaS 能快速验证“预约—派单—完工”，但本项目的长期差异化并不在基础下单，而在以下组合：

- 测漏、防水、水电、清洗、暖气、净水等多业态在同一客户和同一房屋下联动；
- 施工前、中、后证据链以及验收、质保、售后闭环；
- 保利等指定材料的批次、出库、使用位置与质保溯源；
- 散户现结与物业/政企合同、授信、对账并存；
- 上门发现问题后形成“待评估商机”，由公司报价审批，而非师傅私下成交。

因此建议采用“**自建轻核心，分期补强**”：V1 自建关键工单和证据链，支付、短信/隐私号、地图、对象存储等使用成熟云能力，不重复造基础设施。

### 1.4 首版成功标准

首版不是功能上线即成功。建议以一个真实县域、一家物业或企业标杆客户、3–8 名师傅、连续 8 周运营验证以下结果：

- 90% 以上有效订单进入系统；
- 95% 以上完工单具备必填施工前后影像和客户验收；
- 线上/公司统一收款占比达到 90% 以上；
- 投诉能在 3 分钟内调出报价、过程、材料、验收和沟通记录；
- 上门发现的增项线索可跟踪，能够计算“引流单 → 利润单”的真实转化率；
- B 端工单可按客户、项目、结算周期准确对账。
- 企业项目从合同范围、点位报修、批量派工、SLA、验收、对账到回款可以闭环；
- C 端用户能搜索服务、按分类浏览、将多个诉求加入购物车并一次提交，系统再按履约能力合理拆分工单。

## 2. 对合伙人输入的梳理

### 2.1 已具备的业务资源

- 保利水电材料门店：正品背书、材料供应、线下信任入口；
- 精准测漏能力：高信任诊断入口；
- 防水施工团队：高客单工程履约能力；
- 暖气、净水销售安装团队：设备升级和耗材复购能力；
- 家电清洗、水电维修维保团队：高频低门槛上门入口；
- 未来门店、物业与政企关系：品牌展示和稳定订单来源。

### 2.2 核心商业逻辑

以清洗、小额维修、漏水咨询等高频需求获客，通过规范勘察建立信任；发现问题后，将客户转化到精准检测、材料更换、局部改造、防水、暖气净水升级、年度维保等更高价值服务；最终沉淀客户、房屋、设备、施工和质保档案，推动复购与长期合同。

这里需要明确一条产品和经营底线：**“发现问题”必须基于客户授权和可验证证据，不能把上门服务设计成强推销。** 平台应通过照片、检测数据、风险说明、分档方案和二次确认建立信任。

### 2.3 三类目标客户

#### A. 散户业主：现金流与品牌基础

- 需求：清洗、维修、漏水检测、灯具卫浴更换、局部改造、售后；
- 特征：现款、决策快、单量零散、受淡旺季影响；
- 核心体验：透明价格、准时上门、先报价后施工、过程可查、售后有凭证。

#### B. 物业：稳定保底业务

- 公共设施维保：楼道照明、水泵、公共管网等月度/年度包干；
- 业主增值服务：物业导流住户订单，按约定结算或分佣；
- 核心体验：响应时效、批量派单、过程留痕、投诉追责、周期对账。

#### C. 政企/工厂/商铺：高客单与淡季对冲

- 需求：给排水、电路、中央空调、批量设备、定期巡检、防水工程；
- 特征：合同化、多人协作、需审批验收、账期较长；
- 核心体验：项目台账、SLA、报告、验收、发票与回款节点。

### 2.4 业务分层

| 层级 | 典型业务 | 产品作用 | 经营目标 |
|---|---|---|---|
| 引流层 | 家电清洗、小额水电维修、漏水咨询 | 降低首次成交门槛 | 获客、建档、建立信任 |
| 利润层 | 精准测漏、家电维修、局部水电改造、滤芯/配件更换 | 解决明确问题 | 提升客单与毛利 |
| 工程层 | 防水工程、全屋水电翻新、暖气净水整套升级 | 复杂报价与项目履约 | 高客单、高质量交付 |
| 合同层 | 物业包干、政企年度维保、巡检合同 | 周期性履约与结算 | 平滑淡旺季、稳定收入 |

### 2.5 输入材料中的矛盾与产品取舍

1. **装修公司是否为目标客户：** 早期资料把装修公司作为 B 端托底，后续明确“放弃装修公司”。本方案以后续结论为准，V1 不设计装修公司专属流程，仅保留通用“企业客户”扩展能力。
2. **SaaS 还是定制：** 资料建议 3 天采购 SaaS，但当前创业分工和长期壁垒指向自建。本方案建议关键工单自建；若急需验证，可在自建期间用表单/SaaS 过渡，但不要让过渡系统决定长期数据模型。
3. **影像永久保存还是至少两年：** 不应对外承诺“永久”。系统按业务类型配置保留期；重大工程、合同和质保资料跟随合同/质保期限，并支持归档导出。
4. **防私单能力边界：** 隐藏手机号、限制私收款和全程留痕能降低风险，不能从技术上“彻底杜绝”。仍需薪酬、回访、审计、客户权益和劳动制度共同治理。
5. **招商加盟：** “城市代理/全国加盟”属于模式验证后的扩张产品，V1 只做单组织、多团队架构预留，不开发多城市加盟、授权费和总部供应链结算。
6. **盈利与投放数据：** 年利润、毛利、广告 ROI 等均为经营假设，不作为既定事实。系统必须沉淀真实数据后再校准。

## 3. 产品目标与边界

### 3.1 业务目标

- 用标准化服务和数字证据提高陌生客户信任及成交率；
- 将所有订单、报价、材料和收款收口到公司；
- 将一次性服务转化为可持续经营的客户与房屋资产；
- 支持散户现结与 B 端合同结算两种业务模型；
- 形成可复制的工单 SOP，为后续跨区域扩张打基础。

### 3.2 用户目标

- 客户：不用到处找师傅，价格和过程清楚，出现问题找得到责任主体；
- 师傅：任务明确、资料齐全、少来回沟通、提成可核对；
- 调度/客服：订单不漏、异常可见、能快速改派和回访；
- 仓管/门店：材料有来源、出入库有依据、使用去向可追踪；
- 财务/老板：知道收入、成本、毛利、欠款、转化和团队质量；
- B 端客户：知道每个点位发生了什么，能验收、对账、追责。

### 3.3 V1 明确不做

- 不做开放式第三方师傅入驻和竞价抢单平台；
- 不做全国加盟、多城市独立结算和复杂供应链；
- 不做完整 ERP、会计总账和工资发放，只提供业务核算数据；
- 不做 AI 自动诊断、动态定价和复杂智能调度；
- 不承诺真实手机号绝对不可见、照片绝对不可篡改；
- 不把所有服务都设计成可直接一口价下单，复杂工程必须先勘察后报价。

## 4. 产品形态与角色

### 4.1 产品形态

#### 微信小程序

同一个小程序承载两套受权限控制的工作台：

- **客户端：** 服务浏览、预约下单、地址管理、支付、进度、报价确认、施工档案、验收、电子质保、售后、会员权益。
- **师傅工作台：** 待接/待办工单、导航联系、签到、勘察、报价草稿、施工步骤、影像上传、材料登记、验收、异常上报、收入明细。

选择同一小程序的原因是首版成本低、认证和发布链路简单、客户现场验收顺畅。后续师傅规模扩大，再评估独立作业端或企业微信工作台。

#### Web 中后台

- 运营中心：服务商品、价格、活动、优惠券、内容；
- 订单中心：接单、派单、调度、异常、售后；
- 履约中心：SOP、影像审查、报价审批、质保；
- 客户中心：客户、房屋、设备、标签、复购、线索；
- 材料中心：商品、批次、库存、出库、工单用料、溯源；
- B 端中心：客户、合同、项目、点位、SLA、对账、回款；
- 组织权限：员工、班组、角色、服务区域、操作审计；
- 数据中心：经营漏斗、履约质量、人员绩效、应收风险。

### 4.2 核心角色与权限

| 角色 | 核心职责 | 关键权限限制 |
|---|---|---|
| C 端客户 | 下单、确认报价、支付、验收、售后 | 只查看本人及被授权房屋资料 |
| B 端联系人 | 报修、查看项目工单、验收/对账 | 按企业、项目、点位授权 |
| 师傅 | 接单、履约、留证、上报增项 | 不可改最终价格、不可核销公司库存、不可删除证据 |
| 班组长/质检 | 分配班组、复核方案与质量 | 不可调整财务收款数据 |
| 客服/调度 | 建单、预约、派单、改派、回访 | 敏感客户信息按岗位脱敏 |
| 报价审核 | 审核复杂报价和增项 | 报价调整必须留变更记录 |
| 仓管 | 入库、出库、退料、盘点 | 不可修改已完成工单用料 |
| 财务 | 退款、对账、应收、回款登记 | 退款与核销需审批/审计 |
| 管理员/老板 | 配置、看板、审计、权限 | 高危操作二次确认并留日志 |

## 5. 核心业务流程

### 5.1 散户标准订单

1. 客户从广告、二维码、搜索或转介绍进入小程序。
2. 通过搜索、一级/二级分类或推荐进入服务详情，选择服务规格、数量、设备和问题描述。
3. 将一个或多个维修/清洗诉求加入购物车；购物车按服务地址分组，并提示价格模式、预计工单数和不可合并项。
4. 选择房屋地址、联系人和期望时段，补充每个诉求对应的照片/视频；一次提交生成一个客户订单及多个订单项。
5. 系统按服务专业、预约窗口、计价方式和履约班组拆分为一个或多个工单；标准服务支付全款，需勘察服务支付上门费或定金。
6. 系统/调度分配师傅，客户可在订单总览中查看各子工单进度。
7. 师傅到场定位签到，核对服务范围并拍摄施工前照片。
8. 如无增项，按 SOP 施工；如发现新问题，创建“增项/商机”，上传证据并提交报价。
9. 客户在线确认增项与价格后才可继续，重大方案由后台审核。
10. 师傅上传过程、完工、试水/通电等验收资料，登记实际材料。
11. 客户可逐工单验收，订单按应收规则合并或分阶段支付；系统生成服务报告和电子质保凭证。
12. 自动回访，按设备周期触发保养、滤芯更换或再次加入购物车。

### 5.2 复杂工程订单

适用于精准测漏后换管、防水施工、全屋水电改造、暖气净水整套升级：

1. 线索/报修 → 付勘察费 → 上门勘察；
2. 生成勘察报告、风险项和 A/B/C 方案；
3. 后台审核报价 → 客户确认合同/报价 → 支付定金；
4. 排期、材料备货、班组派工；
5. 按关键节点留证并阶段验收；
6. 变更单必须单独确认，禁止口头增项；
7. 竣工验收 → 尾款 → 质保生效 → 档案归档。

### 5.3 物业/政企合同工单

1. 建立企业客户、合同、服务范围、点位、SLA、结算周期和授信上限；
2. 企业联系人/客服提交报修，系统校验合同覆盖范围；
3. 调度按优先级和 SLA 派工，异常即预警；
4. 师傅履约留证，点位负责人验收；
5. 超合同范围的材料/施工生成增项审批；
6. 到结算周期自动汇总可对账工单；
7. 双方确认对账单，财务登记开票与回款；
8. 超期或超授信红线后冻结新非应急工单，由授权人放行。

一期将该流程前置为首要验证链路。企业客户可通过企业联系人小程序、客服代录或批量模板导入报修；同一项目允许一次报修包含多个点位和多个维修诉求，系统按点位、技能和 SLA 拆成可调度工单。包干范围、按次收费、材料另计和审批阈值必须在建单时完成判定。

### 5.4 售后流程

客户发起售后 → 系统判断是否在质保范围 → 客服初审 → 原工单关联 → 派返修/收费复检 → 责任判定 → 处理 → 客户确认 → 质检关闭。所有结论必须关联原报价、影像、材料和验收资料。

### 5.5 工单状态机

`待支付/待确认 → 待派单 → 待接单 → 待上门 → 服务中 → 待报价确认（可选） → 待完工审核 → 待验收/尾款 → 已完成 → 质保中 → 已归档`

异常分支：`已取消`、`已改期`、`待改派`、`暂停施工`、`售后处理中`、`争议中`。任何逆向流转必须填写原因并记录操作者。

## 6. 功能方案

### 6.1 客户端

#### 首页与服务决策

- 首页采用电商平台逻辑：顶部搜索、主类目入口、推荐专区、最近浏览、购物车入口和当前订单；
- 按“家电清洗、家电维修、水电维修、管道疏通、精准测漏、防水施工、暖气净水、安装换新”组织一级类目，并支持二级类目、适用设备和常见故障筛选；
- 搜索覆盖服务名称、设备、故障现象和同义词，例如“跳闸”“没电”“漏水”“洗衣机不脱水”；
- 明确区分“一口价服务”“起步价服务”“勘察后报价”；
- 展示服务范围、不包含项、加价条件、预计时长、质保规则和案例；
- 首页保留漏水/跳闸等紧急入口和人工客服，但不替代分类选购主路径。

#### 购物车与多诉求

- 服务 SKU 可选择规格、数量、服务对象后加入购物车；复杂工程可加入“勘察服务”，不能伪装成固定价商品；
- 购物车按服务地址分组，同一次结算只允许一个服务地址；不同地址分别下单；
- 每个购物车项独立保存设备、故障描述、图片、价格模式和预约要求；
- 实时提示可合并上门、可能拆单、起步价重复计算和服务时间冲突；
- 购物车提交后生成一个订单、多条订单项，后台可拆为多个工单，但客户仍能看到统一订单总览；
- 失效、下架、价格变化或超出服务范围的项目在结算前强提示并要求重新确认；
- 支持再次购买、收藏/常用服务和最近浏览；V1 不做跨商家购物车，因为平台为自营模式。

#### 下单与预约

- 微信授权登录、手机号验证；
- 地址/房屋档案、设备类型与故障描述；
- 订单级统一联系人与地址，订单项级设备、问题和图片/视频；
- 时间段选择时校验全部购物车项，不能履约的项目应拆分预约；
- 优惠券、定金/全款支付、发票信息；
- 下单前确认价格口径、取消规则和隐私授权。

#### 订单与服务档案

- 时间线展示预约、派单、上门、报价、施工、验收；
- 在线确认报价/变更单；
- 查看施工前中后影像、材料清单、检测结果、服务报告；
- 电子验收、电子质保、售后申请、再次下单；
- 对敏感的水电/住址影像进行权限和下载控制。

#### 会员与复购

- 新客券、满减券、复购券、转介绍券；
- 家庭维保次卡/套餐，展示余额、有效期、适用范围；
- 按设备和耗材周期提醒清洗、保养、滤芯更换；
- V1 不做复杂积分商城。

### 6.2 师傅工作台

- 今日待办、可接工单、已接订单、异常工单；
- 地址导航和受控联系客户，敏感信息操作留痕；
- 到达签到：定位、服务时间、异常原因；
- 分业务 SOP：必填检查项、必拍照片位、风险确认；
- 勘察与报价草稿：工时、材料、服务项、方案说明；
- 增项申请：问题证据、建议方案、价格，未经确认不得施工；
- 施工记录：过程图片/视频、检测数值、材料批次/数量；
- 完工自检、现场清理、客户验收码/签字；
- 提成明细只读展示，状态区分“待核算/已确认/已结算”；
- 无网弱网时保存草稿，恢复网络后补传并标记补传时间。

### 6.3 订单与调度后台

- 多渠道建单：客户自助、客服代客、物业/政企报修、线下补录；
- 订单池、地图/列表调度、按技能/区域/班次筛选；
- 自动派单规则作为 P1，V1 先提供规则建议与人工确认；
- 改派、改期、取消、加急、暂停、恢复；
- SLA 倒计时与超时预警；
- 异常中心：未接单、迟到、漏传证据、待审批增项、客户投诉；
- 订单全链路操作日志。

### 6.4 报价、收款与退款

- 服务价格由“工时/服务项 + 材料 + 加急/高空等附加项 - 优惠”组成；
- 标准商品可直接定价，复杂项目支持多方案报价；
- 报价版本化，客户确认后修改必须生成变更单；
- 支持全款、定金+尾款、B 端账期三种结算方式；
- 所有退款必须关联订单、原因、金额和审批记录；
- 系统提供业务对账，不替代财务会计系统。

### 6.5 施工影像与可信档案

- 每个服务模板定义必拍节点：施工前、关键过程、完工、验收；
- 上传时记录服务端时间、工单、操作者、定位授权结果和文件哈希；
- 原图只追加不覆盖，删除采用受控作废并保留审计记录；
- 客户看到经过筛选的交付档案，内部可保留质检资料；
- 证据缺失时工单不能直接完工，需要主管豁免并说明原因；
- 支持生成带品牌、订单号和时间的 PDF/长图服务报告（P1）。

说明：技术只能提高证据可信度，不能宣称“绝对不可篡改”。

### 6.6 材料与溯源

- 材料主数据：品牌、型号、规格、单位、供应商、质保规则；
- 批次/序列号、采购入库、门店/仓库库存；
- 依据已确认报价生成备料单，仓管出库；
- 师傅登记实际使用、退料、损耗和安装位置；
- 完工后客户可查看“本次使用材料”和质保信息；
- 禁止师傅自行新建材料或改成本，临时外采需审批；
- V1 采用轻量库存，不做完整采购财务和多级分销。

### 6.7 客户、房屋与设备档案

- 客户：联系方式、来源渠道、标签、消费、投诉与风险提示；
- 房屋：地址、小区、户型、建成年代（可选）、授权成员；
- 设备：品类、品牌型号、安装时间、历史服务、保养周期；
- 服务资产：管路、防水区域、净水滤芯、暖气系统等档案；
- 一个客户可管理多套房屋，一个房屋可授权多个家庭成员；
- 高价值/敏感标签只对授权岗位可见。

### 6.8 增项与商机管理

这是实现商业闭环的关键功能，但必须避免诱导销售：

- 师傅发现问题后创建商机，必须上传证据并描述风险；
- 商机分为“建议立即处理、建议限期处理、日常保养建议”；
- 客户可选择现在处理、预约复检、暂不处理；
- 高客单项目交由测漏/防水/暖气净水专岗跟进；
- 统计不同引流服务带来的商机率、确认率、成交额和退款投诉率；
- 将高转化与高投诉同时纳入绩效，防止只追求增项金额。

### 6.9 售后与质保

- 服务/材料分别配置质保期限和适用条件；
- 完成验收与结清后生成电子质保凭证；
- 售后申请自动关联原工单、材料、师傅和证据；
- 区分免费返修、客户原因、第三方原因、超质保收费；
- 返修率、一次修复率、争议率纳入团队质量指标。

### 6.10 B 端客户、合同与对账

- 企业、联系人、项目、服务点位；
- 合同有效期、覆盖服务、包干/按单、价格表、SLA；
- 授信额度、账期、欠款红线和暂停规则；
- 多级报修、审批、验收人；
- 周期对账单、工单明细、增项单、发票和回款记录；
- 面向 B 端联系人提供轻量小程序视图，不单独开发门户。
- 支持企业联系人一次提交多个点位/多个诉求，或通过标准模板批量导入；
- 项目工作台展示合同额度、已用金额、剩余额度、SLA 风险、待验收、待对账与逾期应收；
- 支持“物业公共区域包干维保”和“物业推荐业主自费服务”两类业务隔离，佣金/渠道归因不得混入企业合同应收；
- 一期围绕约 10 万元级企业维保项目建立项目预算、维修任务包、阶段验收、材料审批与周期对账能力。

### 6.11 经营数据

首版建议只做能驱动动作的看板：

- 获客：渠道订单量、获客成本、首单支付率；
- 转化：引流单完工率、增项发现率、报价确认率、利润单转化；
- 履约：准时率、平均响应/完工时间、证据完整率、取消率；
- 质量：好评率、返修率、投诉率、一次修复率；
- 财务：实收、退款、材料成本、预估毛利、应收和逾期；
- 人员：工单数、工时、客诉、复购、质量分；
- B 端：合同消耗、SLA 达成、应收余额、超授信客户。

### 6.12 服务商品与维修 SKU 管理后台

维修 SKU 是平台统一主数据，必须由 React 管理后台集中管理。微信小程序、客服建单、企业报价和师傅履约只能引用已发布 SKU，禁止在各端硬编码服务名称、价格、规格或质保规则。

#### SKU 管理范围

- 类目：一级/二级分类、客户端名称、图标、排序、启停和适用客户类型；
- SPU/服务商品：标题、副标题、主图/详情图、服务说明、适用场景、案例、常见问题；
- SKU/服务规格：规格名称、服务对象、计价单位、数量规则、一口价/起步价/检测后报价；
- 价格：基础价格、划线价、上门费、起步费、加急/高空等附加规则、企业合同价引用；
- 服务范围：可售区域、可预约时段、所需技能、预计工时、是否可合并上门；
- 履约：SOP、必填检测项、必拍证据、所需材料、验收项和质保规则；
- 交易：上下架时间、产能占位方式、取消退款规则、发票分类、优惠适用性；
- 搜索：关键词、设备词、故障词、同义词、搜索权重和推荐标签。

#### 生命周期与发布

`草稿 → 待审核 → 已发布 → 已停用/已下架 → 已归档`

- 运营可创建和编辑草稿，价格、履约范围、质保、SOP 等关键字段变更需审核；
- 发布必须生成不可变版本，并同步小程序目录、搜索索引和购物车校验；
- 已产生订单的 SKU 不允许覆盖历史版本，订单保存下单时完整快照；
- 下架后不允许新加入购物车，已有购物车项标记失效，历史订单与售后仍可读取原版本；
- 支持定时上下架、复制 SKU、批量调整分类/区域、版本对比和基于历史版本创建新草稿；
- 删除仅适用于从未发布的草稿，已发布 SKU 只能停用或归档。

#### 权限与审核

- 商品运营：维护分类、图文、搜索词和草稿；
- 价格管理员：维护价格和优惠边界；
- 履约负责人：维护技能、SOP、证据、验收与质保；
- 审核/发布人：查看版本差异并发布，关键变更遵循编辑与发布分离；
- 所有发布、下架、价格调整和批量修改写入审计日志。

#### 小程序消费规则

- 小程序启动和进入分类/详情时从后端读取已发布目录，不携带业务 SKU 常量；
- 分类、搜索、详情、购物车和结算使用同一发布版本口径；
- 客户结算前必须重新校验 SKU 状态、版本、价格、区域和预约约束；
- 配置不可用时允许展示最近一次有效缓存，但禁止用过期价格创建订单。

## 8. 关键数据模型

核心对象及关系建议如下：

- **组织域：** 公司 → 网点/仓库 → 部门/班组 → 员工 → 角色权限；
- **客户域：** 客户 → 房屋/企业 → 设备/点位 → 联系人/授权成员；
- **商品域：** 服务类目 → 服务 SKU → 价格规则 → 服务 SOP/质保规则；
- **交易域：** 订单 → 预约 → 工单 → 报价/变更单 → 支付/退款 → 发票；
- **履约域：** 签到 → 检查项 → 影像证据 → 材料使用 → 验收 → 服务报告；
- **售后域：** 质保凭证 → 售后单 → 责任判定 → 返修工单；
- **供应域：** 材料 SKU → 批次/序列号 → 库存流水 → 出库/退料 → 工单用料；
- **B 端域：** 企业 → 合同 → 项目/点位 → SLA → 对账单 → 回款；
- **增长域：** 渠道 → 活动/优惠券 → 线索/商机 → 转化结果。

所有核心业务记录建议使用不可变 ID；金额、状态、报价、库存和权限变化均保留操作日志，避免只保存“最新值”。

## 9. 关键规则与非功能要求

### 9.1 关键业务规则

1. 未经客户确认的增项不得开工；紧急止损场景也需记录口头授权并事后补确认。
2. 已确认报价只能通过变更单调整，禁止覆盖原报价。
3. 必填证据不完整不能正常完工，主管豁免必须可审计。
4. 实际用料应从已出库/批准外采材料中选择。
5. 散户原则上结清后完成；B 端按合同校验额度、账期和验收人。
6. 退款、作废证据、改单、库存调整、超授信放行均属于高危操作。
7. 客户可查看与其服务相关的数据；员工只按岗位和当前任务访问最少必要信息。

### 9.2 隐私与安全

- 收集定位、住址、电话、房屋内部影像前明确告知用途并取得授权；
- 客户手机号与详细地址按岗位脱敏，导出需要权限；
- 图片对象存储使用私有访问和短时签名链接；
- 敏感操作、登录、导出、改价、退款均记录审计；
- 数据备份、恢复演练、离职账号即时停用；
- 上线前由专业人士核对隐私政策、用户协议、支付、用工、发票、保险和具体业务资质要求。

### 9.3 性能与可靠性

- 小程序核心页面在普通 4G 环境下可快速打开；
- 图片采用压缩、断点/失败重传，原图后台异步归档；
- 支付和状态流转必须幂等，避免重复扣款或重复完工；
- 关键通知同时进入站内消息，不能只依赖一次性订阅消息；
- 监控订单创建、支付回调、派单、图片上传、退款等关键链路。

## 10. 指标体系与验收

### 10.1 北极星指标

**每月“完成验收且证据完整”的有效工单数，以及这些工单带来的 90 天复购/增项毛利。**

单看 GMV 容易诱导过度增项；单看订单量又会忽略利润和质量，因此必须把“可信完工、后续价值、投诉退款”一起看。

### 10.2 首期核心指标

| 维度 | 指标 | 首期建议目标 |
|---|---|---|
| 数字化 | 系统入单率 | ≥ 90% |
| C 端选购 | 搜索有结果率 | ≥ 90%，并持续维护同义词 |
| C 端选购 | 购物车提交率 | 建立基线，重点分析价格/预约阻塞 |
| C 端结构 | 多诉求订单占比 | 建立真实基线，验证合单价值 |
| 履约 | 必填证据完整率 | ≥ 95% |
| 履约 | 准时到达率 | ≥ 90% |
| 交易 | 公司统一收款占比 | ≥ 90% |
| 转化 | 增项报价确认率 | 先建立基线，不预设夸张目标 |
| 质量 | 7/30 天返修率 | 按服务类目建立基线并持续下降 |
| 客户 | 完工评价率 | ≥ 60% |
| 风险 | B 端逾期应收占比 | 受控且不突破授信红线 |
| B 端履约 | SLA 按时响应率 | ≥ 95% 或按合同目标 |
| B 端项目 | 项目预算/合同消耗可核对率 | 100% |

### 10.3 V1 发布验收场景

- 管理员在后台新建“插座更换”SKU，配置规格、价格、区域、SOP、证据和质保，审核发布后在小程序分类与搜索中可见；
- 后台调价后，已有购物车提示价格变化并要求重新确认，历史订单继续显示原成交快照；
- 后台下架 SKU 后，新用户无法加入购物车，已有购物车项失效，但原订单仍能履约和售后；
- 客户搜索“跳闸”，找到正确服务并与“油烟机清洗”一起加入购物车；
- 同一地址两个诉求一次提交后拆成不同专业工单，订单总览和金额仍然清楚；
- 客户独立完成清洗一口价订单并验收；
- 客服代客创建老人订单，客户现场扫码验收；
- 维修订单现场发现增项，报价确认后支付差额；
- 师傅迟到、拒单、改派、材料不足、无网补传均能闭环；
- 客户投诉时能完整还原下单、报价、施工、材料、验收；
- 财务能够核对订单应收、实收、退款；
- 权限测试确保师傅无法修改价格或查看无关客户数据。
- 企业联系人一次提交多个点位维修任务，调度批量拆单并按 SLA 跟踪；
- 约 10 万元级企业项目完成合同规则校验、材料审批、阶段验收、对账与回款登记。

## 11. 落地节奏与团队建议

### 阶段 0：业务定版（1–2 周）

- 选出首发 15–25 个服务 SKU；
- 为清洗、维修、勘察、工程各选 1 个典型服务；
- 定义报价口径、质保、取消、退款和材料规则；
- 跟随师傅完成至少 5–10 次真实上门，记录异常；
- 确认支付主体、微信小程序认证主体和客服流程。
- 明确“10 万单”的业务口径：若指 10 万元项目，确认预算、工单规模和结算节点；若指 10 万张工单，需重新评估组织、容量、搜索与调度架构。
- 取得首期物业/企业合同样本、点位清单、维修任务清单、SLA、审批和对账样表。

### 阶段 1：V1 研发（10–12 周）

- 第 1–2 周：原型、数据模型、权限、技术基座；
- 第 3–5 周：分类、搜索、购物车、多订单项、企业/合同/点位；
- 第 6–8 周：批量建单、订单拆工单、师傅履约、后台调度与 SLA；
- 第 9–10 周：报价支付、影像、材料、验收、对账、售后与审计；
- 第 11–12 周：企业项目与 C 端真实订单试运行、修复、埋点和运营培训。

### 阶段 2：单城试运营（8 周）

- 只在一个服务区域、一个团队上线；
- 每周复盘漏单、线下绕单、证据缺失、客户卡点；
- 先修流程和规则，再加营销功能；
- 达到首版成功标准后进入 P1。

### 最小产品团队

- 业务负责人/合伙人：服务标准、价格、团队和客户验证；
- 产品负责人：流程、规则、原型、数据和验收；
- 技术负责人/全栈：架构、研发、上线与可观测性；
- UI/交互：可兼职或阶段性投入；
- 测试/运营：试运营期必须有人承担，不建议完全由开发自测。

## 12. 主要风险与应对

| 风险 | 典型表现 | 产品与经营应对 |
|---|---|---|
| 范围失控 | 多业态、B 端、加盟同时开工 | V1 只做三种订单模型和一个组织 |
| 师傅抵触 | 录入步骤多、现场网络差 | SOP 模板化、默认值、弱网草稿、减少重复输入 |
| 过度销售 | 为增项而制造焦虑 | 证据+分级建议+客户确认，质量与投诉反向约束绩效 |
| 私单 | 留电话、私收款、线下续单 | 权限脱敏、统一支付、回访、权益绑定、薪酬与审计联合治理 |
| 纠纷 | 口头报价、范围不清、变更无记录 | 标准范围、报价版本、变更单、过程证据、电子验收 |
| 图片成本与隐私 | 大量照片长期保存、内部影像泄露 | 分级保留、压缩归档、私有存储、下载与导出审计 |
| B 端现金流 | 长账期、无限垫资 | 授信额度、逾期预警、暂停规则、单独核算 |
| 数据失真 | 毛利只算收入不算材料/返修/广告 | 建立订单级收入、材料、退款、返修和渠道成本口径 |
| 资质安全 | 高空、水电、特种作业事故 | 人员证照/保险到期提醒，派单前资格校验，专业法务与安全审核 |

## 13. 创始人必须先拍板的 12 个问题

1. 首发县域、服务半径和营业时段是什么？是否提供 24 小时应急？
2. 首发 15–25 个服务 SKU、价格类型和质保规则分别是什么？
3. 哪些业务自营，哪些由合作班组履约？合作班组是否允许接触客户？
4. 复杂项目的报价审核人、金额阈值和折扣权限是什么？
5. 清洗上门发现问题后，什么属于合理建议，什么禁止现场推销？
6. 材料是否全部由门店出库？紧急外采和客户自备材料如何处理？
7. 客户取消、师傅空跑、二次上门、夜间加急如何收费？
8. 影像分别保存多久？哪些照片客户可见，哪些仅内部质检可见？
9. 师傅联系客户采用隐私号、企业电话还是阶段性显示号码？
10. 物业/政企首期是否真的有种子客户？合同、对账和授信最小需求是什么？
11. V1 是正式自建上线，还是先用 4–6 周过渡工具验证流程？
12. 品牌名称、主体、微信支付商户、发票主体和售后责任主体是否一致？

## 14. 最终建议

先不要以“功能大全”开工，也不要以“全国加盟”倒推架构。第一阶段只做一件事：**让一张真实订单从获客到质保完整在线闭环，并且比微信群、电话和纸质工单更可信、更省事。**

产品的第一壁垒不是页面数量，而是服务标准被系统真实执行；第二壁垒是客户、房屋、设备、材料和施工证据持续沉淀；第三壁垒才是多业态交叉转化和 B 端长期合同。按照这个顺序建设，软件才会成为经营能力，而不是另一套需要员工额外维护的台账。
