## 1. 交付结果

1. 下单页仅突出地址、白天上门时间、服务摘要和总价，默认地址有效时只需选择时间、核对信息并提交。
2. 结算页删除服务说明／须知及其展开入口，仅保留一个“订单备注”选填入口；不填写、不上传也能下单。
3. 预约仅提供 08:00、10:00、12:00、14:00、16:00 五个起始时刻，每段两小时，18:00 前结束；前后端及履约相关时段定义统一，不再保留晚间旧订单兼容分支。
4. 下单后可修改备注、补充或移除当前现场资料；保存后可重新读取，后台和已派单师傅刷新能看到最新内容。
5. 保留两种结算来源、真实金额、用户隔离、订单快照、现有支付跳转及履约流程。

不扩展优惠、费用、聊天、通知、师傅确认阅读或通用备注平台。结算页不新增数量编辑。

## 2. 当前代码基线与实施原则

| 已有能力 | 实施决策 |
| --- | --- |
| `checkout/index.ts` 支持立即下单和购物车勾选结算 | 保留各自参数及需求保存路径，只整理页面状态与展示数据 |
| 下单前需求按购物车服务项归属，直接下单通过 `directItem` 提交 | 备注编辑器按稳定服务项 ID 管理，不新增订单级模糊备注字段 |
| `order_item.demand_description`、`order_item_media` 保存订单需求 | 继续作为当前需求的数据源；新接口写订单，不回写购物车 |
| 客户订单详情由 `internal/fulfillment/service.go` 读取 | 统一新增字段及订单需求查询，避免订单详情和编辑器回显不一致 |
| 工单详情已经关联 `order_item` 读取文字及媒体 | 优先复用关联查询，不复制需求到工单快照；补齐必要的客户端展示 |
| 媒体已有上传、私有读取、引用删除保护 | 沿用授权链路，增加历史需求媒体引用保护；不改为公开 URL |
| 订单创建和履约读取有不同的时段校验／标签逻辑 | 现有订单清空后统一为五个白天时段，删除晚间兼容逻辑 |
| 订单创建已有幂等记录 | 需求更新复用既有设施，键需区分操作及订单，不能与创建订单串用 |

执行前记录现有未提交修改，不覆盖其他功能。所有下列文件名及迁移号在落地时再次核对，编号冲突时顺延。

## 3. 数据与接口方案

### 3.1 从空订单数据建立新结构

- 在 `customer_order` 增加独立 `demand_version`，非空、初值 0。需求更新不递增支付／履约使用的订单 `version`，避免无关操作发生冲突。
- 保持现有 `order_item` 文字及 `order_item_media` 当前关联结构，更新仍按服务项保存。
- 新增订单需求变更记录表：组织、订单、客户操作人、变更前后需求快照、需求版本及时间；快照包含服务项 ID、文字和有序媒体 ID。只为本功能留存必要历史。
- 新增变更记录媒体关联表，通过实际媒体引用保护历史文件，不只把媒体 ID 存在 JSON 中。唯一约束避免同一次变更重复引用同一媒体，索引支持按媒体查询。
- 不保留、不转换现有订单，不实现旧订单首次更新回填或旧格式兼容。清理后新建的订单从初始需求开始记录后续变更，追溯规则只面向新流程产生的数据。
- 迁移暂定 `000023_order_demand_updates.up.sql`／`.down.sql`，当前最大号为 000022；执行前重新检查。提供结构回退脚本；开发验收数据需要重建时按本计划清理后重新生成，不设计存量订单恢复迁移。

### 3.2 客户需求接口

| 接口 | 契约 |
| --- | --- |
| `GET /api/v1/mini/orders/{id}/demand` | 返回 `demandVersion`、`editable`、只读原因、按服务项组织的名称、备注和授权媒体信息 |
| `PUT /api/v1/mini/orders/{id}/demand` | 接收 `demandVersion` 及该订单全部服务项的 `itemId`、`demandDescription`、有序 `mediaIds`；整次保存原子成功或失败 |

- ID 沿用现有字符串契约；文字上限 500 字、去除首尾空白后校验；媒体规则复用现有上传约束。禁止遗漏、重复或混入其他订单服务项。
- 查询校验组织、登录客户及订单归属，私有资料返回客户可授权读取的地址；不能返回后台专用地址供客户直接访问。
- 更新事务先验证身份及订单归属，锁定订单并检查状态、需求版本，再校验服务项及媒体。按固定顺序锁定引用媒体，与媒体删除保护串行化，避免引用已删除资源。
- 媒体必须属于当前客户、当前组织，目的为现场需求、状态为有效；不能通过伪造 ID 引入他人附件或商品图片。
- 同一事务内更新文字和当前媒体关联、写入变更历史及历史媒体引用、递增需求版本、完成幂等响应；任一步失败全部回滚。
- 更新采用 `Idempotency-Key`，请求哈希包含操作、订单及正文；同键同请求重放原成功结果，不重复写历史；同键不同请求返回冲突。网络结果未知时使用原键重试，用户编辑请求后生成新键。
- 版本冲突返回 409 及中文提示，前端保留本地输入，让用户重新加载后核对；不能用强制覆盖自动解决。
- 以 `PENDING_CONFIRMATION`（包含待支付展示状态）及 `FULFILLING` 为可编辑白名单；待派单、已派单、服务中通过现有订单／工单状态映射，不新增数据库订单状态。`WAITING_ACCEPTANCE` 及完成、取消、关闭、未知状态只读；售后不自动解锁原备注。
- 状态变更与需求保存采用一致的订单锁顺序；编辑中支付超时或订单结束时，服务端拒绝保存。成功重放只返回原结果，不再次写入。
- 建议错误码：`ORDER_DEMAND_VERSION_CONFLICT`、`ORDER_DEMAND_READ_ONLY`；字段及媒体错误沿用现有校验响应。不得向无权访问者泄露订单内容。

## 5. 验证与验收

### 5.1 必要服务端验证

围绕真实风险新增／调整单元及数据库集成验证，不为静态样式编写镜像测试。

| 验证组 | 必须覆盖 |
| --- | --- |
| 预约 | 五个白天时段接受，18:00／20:00 及未知值拒绝；日期边界按北京时间；派单／改约及验收时间计算使用相同时段定义 |
| 需求保存 | 纯文字、纯媒体、组合、清空当前需求、多服务项同时更新；历史前后快照、顺序和版本正确 |
| 权限 | 他人订单、跨组织、伪造服务项、他人媒体、错误用途及无效媒体拒绝；错误不泄露资料 |
| 原子性 | 任一项媒体不合法时所有文字、附件、版本及历史均不变 |
| 并发 | 两客户端同时保存仅一份新版本生效；结束／取消与保存竞争时不突破状态限制 |
| 幂等 | 同键同正文重试不重复写记录；不同正文冲突；不与创建订单共用键空间 |
| 媒体引用 | 当前需求移除后历史引用仍阻止删除；删除与新增引用并发时不会产生悬空引用 |
| 数据保全 | 需求更新前后数量、价格、商品快照、支付及履约状态保持一致，原订单版本不因备注变更而失效 |
| 履约查看 | 更新后后台及已派单师傅读取最新文字和附件；无权师傅不能读取 |
