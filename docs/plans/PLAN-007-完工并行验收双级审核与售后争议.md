# PLAN-007｜完工并行验收、双级审核与售后争议实施计划

**状态：** Planned  
**版本：** V1.0  
**日期：** 2026-08-10  
**对应 Spec：** `docs/specs/SPEC-007-完工双级审核客户验收与售后争议.md` V1.3  
**适用工程：** `apps/server-go`、`apps/admin-web`、`apps/wechat-mini`、`apps/wechat-worker-mini`

## 1. 交付目标

将当前单级完工审核链路升级为：

```text
师傅提交完工
├→ 客户立即验收和一次性评价
└→ 审核员初审 → 总监终审
                 ↓
              结果汇合
```

并完整支持：

- 客户拒绝后立即二次上门；
- 完工满7天系统自动验收；
- 人工验收和系统自动验收来源区分；
- 客户已验收但内审不通过时进入客服确认；
- 客服确认需要二次上门时复用客户驳回链路；
- 客服确认无需二次上门时独立打标、筛选和完整追溯；
- 已完成后的投诉和质保返修不重开原工单。

## 2. 实施原则

1. 客户验收和内部审核使用独立状态字段，不继续扩展单一 `work_order.status` 表达所有组合。
2. 审核员和总监内部串行，客户分支与内部审核并行。
3. 客户拒绝验收优先触发二次上门，不等待内部审核结束。
4. 客户已验收但内审不合格时，必须由客服确认，不能由系统直接关单或返修。
5. 评价只允许创建一次，不提供更新和删除接口。
6. 所有历史、审核、评价、客服确认和上门轮次只追加，不覆盖旧记录。
7. 所有状态命令具备事务、乐观锁、幂等键和组织/角色校验。
8. 已执行 migration 不修改，只新增向前 migration。
9. 每个阶段完成对应验证后再进入下一阶段，不顺带重构无关模块。

## 4. R0｜规则、角色和接口冻结

### R0-1｜冻结正交状态模型

确定四个独立状态维度：

- `visit_status`：作业轮次；
- `customer_acceptance_status`：客户验收；
- `internal_review_status`：内部审核；
- `closure_status`：汇合和关单。

确定结案结果：

- `NORMAL`；
- `SECOND_VISIT_COMPLETED`；
- `CUSTOMER_CONFIRMED_NO_SECOND_VISIT`；
- `CANCELLED`。

验证：逐项列出所有合法转换和拒绝转换，任何场景不依赖前端自行推导。

### R0-2｜冻结角色和职责隔离

新增业务角色：

- `QA_REVIEWER`；
- `QA_DIRECTOR`；
- `AFTER_SALES_AGENT`；
- `AFTER_SALES_MANAGER`；
- `DISPATCHER`。

规则：

- 执行师傅不能审核自己的提交；
- 初审员和总监不能是同一账号；
- `ADMIN` 不自动拥有审核员或总监业务权限；
- 客服确认和审核决定必须记录实际操作账号。

### R0-3｜冻结 API 和错误码

在 OpenAPI 中定义：

- 完工提交批次；
- 客户验收和评价；
- 初审队列、初审命令；
- 总监队列、终审命令；
- 客服确认；
- 二次上门轮次；
- 结案结果筛选；
- 完整工单时间线；
- 售后案件和返修工单。

所有命令接口明确 `Idempotency-Key`、`version`、角色和错误码。

退出条件：状态转换表、角色矩阵、接口契约和测试场景逐项对应 SPEC-007。

关键约束：

- 每工单轮次的 `attempt_no` 唯一；
- 每提交批次最多一条客户验收和一条评价；
- 评价表不提供更新路径；

- `completion_outcome` 仅在关单时写入；
- `(org_id, completion_outcome, closed_at DESC)` 索引可用。

### R1-2｜存量迁移

- `WAITING_COMPLETION_REVIEW`：迁移为客户待验收、内审待初审；
- `WAITING_ACCEPTANCE`：生成 `LEGACY_MIGRATION` 内审通过记录，客户保持待验收；
- `FINISHED`：保留完成时间，结案结果设为 `NORMAL`；
- `REWORK_REQUIRED`：保留状态，在下次履约时创建新轮次；
- 历史完工证据绑定到首个迁移提交批次；
- 不修改既有订单、工单和媒体主键。

### R1-3｜仓储和事务边界

建立最小领域仓储：

- 完工提交；
- 客户验收/评价；
- 两级审核；
- 汇合决策；
- 客服确认；
- 上门轮次；
- 售后案件；
- 时间线查询。

退出条件：空库 migration、存量升级、down 回滚和真实 PostgreSQL 约束测试通过。

## 6. R2｜完工提交与并行启动

### R2-1｜重构完工提交事务

师傅提交完工时，在同一事务内：

1. 校验当前师傅、轮次、状态、版本和前后证据；
2. 创建不可修改的 `completion_submission`；
3. 冻结本批次证据快照；
4. 初始化 `customer_acceptance_status=PENDING`；
5. 初始化 `internal_review_status=PENDING_QA`；
6. 创建客户验收待办；
7. 创建审核员初审待办；
8. 写入统一事件历史。

任一步失败必须整体回滚。

### R2-2｜师傅端适配

- 提交后展示“客户验收中”和“平台质检中”两个进度；
- 不再展示单一“等待后台审核”；
- 查看当前轮次、历史提交和公开驳回意见；
- 二次上门使用新的轮次和提交批次。

验证：一次提交只产生一个提交批次、一个客户待办和一个初审待办；幂等重试不重复创建。

## 7. R3｜客户验收、一次性评价与自动验收

### R3-1｜客户立即验收

师傅提交后，客户小程序立即展示：

- 完工说明和客户可见证据；
- 人工确认完成；
- 拒绝验收；
- 评价入口；
- 7天自动验收提示。

人工通过写入 `MANUAL_ACCEPTED`；拒绝时原因、问题类型必填并支持图片/视频。

### R3-2｜一次性评价

- 每个提交批次只允许提交一次；
- 数据库唯一约束兜底；
- 提交前弹出“评价提交后不可修改”二次确认；
- 不实现 PUT/PATCH/DELETE 评价接口；
- 重复提交返回 `RATING_ALREADY_SUBMITTED`；
- 评价缺失不阻塞验收和审核。

### R3-3｜7天自动验收任务

实现可重复扫描任务：

- 基准时间为本轮 `completion_submission.submitted_at`；
- 提交时立即告知7天规则；
- 第3天、第6天生成提醒；
- 满 `7×24` 小时且仍为 `PENDING` 时写入 `AUTO_ACCEPTED`；
- 自动任务使用业务幂等键和数据库条件更新；
- 人工与自动竞争时只能有一条最终验收记录；
- 自动验收必须保留系统任务 ID 和事件历史。

退出条件：人工/自动验收在接口、数据库、后台和小程序中均可区分；并发测试只有一个结果。

## 8. R4｜审核员初审与总监终审

### R4-1｜初审队列和操作

- 仅 `QA_REVIEWER` 可访问；
- 展示执行师傅、提交批次、完工说明、证据、客户验收来源和评价；
- 客户未操作时明确显示“待验收”；
- 审核员给出通过/驳回建议、问题项和说明；
- 驳回建议原因必填并二次确认；
- 初审完成后统一进入总监队列，不直接触发返修。

### R4-2｜总监终审

- 仅 `QA_DIRECTOR` 可访问；
- 展示初审人、初审决定、客户验收和评价；
- 总监与初审员、执行师傅必须不同；
- 可以确认或推翻初审建议，推翻时原因必填；
- 终审结果为内部 `APPROVED` 或 `REJECTED`；
- 提交审核时校验客户反馈版本，变化后提示刷新。

### R4-3｜后台角色入口

- 履约调度增加待初审、待总监终审队列；
- 菜单和按钮按业务角色展示；
- 后端权限校验不依赖前端隐藏；
- 审核记录只追加，不允许修改或删除。

退出条件：职责隔离、越权、并发审核、重复审核和客户反馈版本变化测试通过。

## 9. R5｜结果汇合、客服确认与二次上门

### R5-1｜实现汇合决策器

集中实现以下规则：

| 客户结果 | 内审结果 | 动作 |
| --- | --- | --- |
| 人工/自动通过 | 通过 | 正常关单 |
| 拒绝 | 任意 | 立即二次上门 |
| 人工/自动通过 | 不通过 | 进入客服确认 |
| 待验收 | 通过 | 等待客户或7天自动验收 |
| 待验收 | 不通过 | 等待7天自动验收，随后进入客服确认 |

汇合决策必须由后端服务统一执行，并支持在客户、审核或自动任务任一分支结束时重新计算。

### R5-2｜客户拒绝和二次上门

客户拒绝事务内：

- 写入 `REJECTED`；
- 创建 `ACCEPTANCE_REJECT` 售后案件；
- 创建 `cycle_no + 1` 上门轮次；
- 工单进入 `SECOND_VISIT_PENDING`；
- 未结束内审转为非阻塞质量追踪；
- 调度选择原师傅或改派。

### R5-3｜客服确认

客户已验收、内部终审不通过时：

- 工单进入 `WAITING_CUSTOMER_SERVICE_CONFIRMATION`；
- 客服待办展示验收来源、评价和审核驳回原因；
- 客服填写联系时间、方式、沟通备注和客户决定；
- “需要二次上门”复用 R5-2 的售后案件和上门轮次事务；
- “不需要二次上门”必须二次确认并进入异常关单；
- 联系不上时保持待确认，不允许自动选择。

退出条件：结果矩阵所有组合均有服务测试；同一汇合事件重复计算不产生重复轮次或客服记录。

## 10. R6｜独立结案标记、筛选与完整时间线

### R6-1｜无需二次上门结案

客服确认客户不需要二次上门时，在同一事务中：

- `closure_status=FINISHED_WITH_REVIEW_EXCEPTION`；
- `completion_outcome=CUSTOMER_CONFIRMED_NO_SECOND_VISIT`；
- `has_review_exception=true`；
- 写入 `closed_at`、`closed_by` 和客服确认记录 ID；
- 写入只追加关单事件；
- 订单重新执行完成汇总；
- 不改变内部终审 `REJECTED`。

### R6-2｜列表筛选和标签

扩展后台工单列表：

```http
GET /api/v1/admin/work-orders?completionOutcome=CUSTOMER_CONFIRMED_NO_SECOND_VISIT
```

列表返回并展示：

- 结案结果；
- 人工/自动验收来源；
- 内部审核结果；
- 是否存在审核异常；
- 橙色标签“客户确认无需二次上门”。

验证：真实 PostgreSQL 使用结案结果索引，筛选结果准确且分页总数一致。

### R6-3｜完整工单时间线

实现：

```http
GET /api/v1/admin/work-orders/{id}/timeline
```

聚合并按时间、事件序号排序：

- 下单、确认、派单、改派、预约；
- 所有上门轮次；
- 完工提交和证据快照；
- 人工/自动验收和一次性评价；
- 初审、终审；
- 客服确认；
- 二次上门、投诉、售后；
- 关单和质保生效。

时间线事件必须包含角色、操作人、前后状态、公开说明和内部备注权限，不能由前端根据当前状态拼接。

退出条件：可通过筛选定位目标工单，并从详情还原完整业务过程。

## 11. R7｜投诉、质保和已完成返修

### R7-1｜售后案件后台

- 客户可在履约中、待验收和质保期内发起投诉；
- 客服完成分类、严重度、判责和方案；
- 售后主管批准返修、改派、补偿或退款方案；
- 所有沟通、证据和决定进入案件时间线。

### R7-2｜已完成工单返修

- 原工单保持 `FINISHED` 或 `FINISHED_WITH_REVIEW_EXCEPTION`；
- 创建独立返修工单并关联原工单和售后案件；
- 返修工单独立派单、履约、并行验收和两级审核；
- 原工单质保和历史不被覆盖。

退出条件：验收前二次上门与完成后质保返修使用不同模型，数据关系和页面展示清晰。

## 12. R8｜四端交付与完整验收

### R8-1｜客户小程序

- 完工后立即验收和评价；
- 评价提交前二次确认，提交后不可编辑；
- 展示7天自动验收倒计时和提醒；
- 明确区分人工验收和系统自动验收；
- 客户拒绝后展示二次上门进度；
- 客服确认阶段展示“客服确认中”。

### R8-2｜师傅小程序

- 展示客户验收和平台质检两个进度；
- 查看驳回原因、二次上门轮次和新提交入口；
- 历史提交和证据只读；
- 不展示内部责任判定和客服内部备注。

### R8-3｜管理后台

- 初审、终审、客服确认和售后队列；
- 查看客户验收、评价和全部作业证据；
- 结案结果筛选和标签；
- 完整工单时间线；
- 角色权限和操作审计。

### R8-4｜真实 PostgreSQL 与 E2E

至少执行以下链路：

```text
后台派单
→ 师傅履约并提交
→ 客户人工验收和评价
→ 审核员初审
→ 总监终审驳回
→ 客服确认客户需要二次上门
→ 二次上门并重新提交
→ 系统满7天自动验收
→ 内部终审通过
→ 工单完成
```

另执行目标标记链路：

```text
客户人工验收
→ 内部终审驳回
→ 客服确认客户不需要二次上门
→ 写入 CUSTOMER_CONFIRMED_NO_SECOND_VISIT
→ 后台筛选命中
→ 时间线完整展示
```
