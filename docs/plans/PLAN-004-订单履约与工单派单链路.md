# PLAN-004｜订单履约与工单派单链路实施计划

**状态：** Planned  
**版本：** V1.0  
**日期：** 2026-08-09  
**对应 Spec：** `docs/specs/SPEC-004-订单履约与工单派单链路.md` V1.0  
**适用工程：** `apps/server-go`、`apps/admin-web`、`apps/wechat-mini`  
**执行顺序：** 数据与状态机 → 订单确认 → 师傅与派单 → 师傅履约 → 审核与客户验收 → 并发、权限与 E2E

---

## 1. 交付目标

在现有 SKU、购物车和下单能力之上，跑通以下可演示、可追溯的履约闭环：

```text
客户下单
→ 后台确认订单并按订单项生成工单
→ 后台设置上门时间并派单
→ 师傅接单、到达、开始服务
→ 师傅上传施工前后图片并提交完工
→ 后台审核完工
→ 客户确认验收
→ 工单完成并汇总订单完成
```

完成时必须满足：

- 一条订单项只生成一张主工单，确认重试不重复拆单；
- 所有状态变更只能通过命令接口，并留下操作人、原因和时间历史；
- 管理员、客户、师傅只能访问和操作其权限范围内的数据；
- 派单、履约、审核和验收具备乐观锁与幂等保护；
- PostgreSQL、Go API、React 管理后台和微信小程序的完整链路通过；
- SPEC-004 的 AC-FUL-01 至 AC-FUL-10 全部通过。

## 2. 基线、假设与边界

### 2.1 当前基线

- Go 后端已有 `catalog`、`cart`、`media`、`order` 模块；
- PostgreSQL 已有订单、订单项、员工、工单及工单状态历史的基础结构；
- 后台已有订单列表和详情，工单管理仍为占位页面；
- 小程序已有下单能力，“我的订单”和师傅工作台尚未形成履约闭环；
- 当前下单状态是 `WAITING_PAYMENT`，但系统没有支付实现。

### 2.2 本计划采用的确定性决策

1. 新订单直接进入 `PENDING_CONFIRMATION`，本期不伪造支付完成事件。
2. 一个 `order_item` 生成一张 `work_order`，数量不进一步拆分。
3. 首期只做人工派单，不实现技能、班次、距离或路线算法。
4. 师傅端继续承载在微信小程序内，用开发环境 token 模拟身份。
5. 完工至少需要一张 `BEFORE`、一张 `AFTER` 图片及 5—1000 字说明。
6. 订单状态是工单状态的服务端汇总结果，前端不能直接修改。

### 2.3 明确不做

- 微信支付、报价、退款、发票；
- 智能派单、抢单、排班和地理围栏；
- 材料库存、成本和师傅结算；
- 企业批量订单、SLA、质保和返修工单；
- 为未来场景建设通用工作流引擎或通用拆单引擎。

## 3. 实施原则

1. 不修改已发布 migration，只新增向前 migration。
2. 状态规则集中在 Go 领域服务中，不散落到 Handler 和前端。
3. 每个命令先验证身份、组织、资源归属、状态和版本，再写数据库。
4. 主表更新、历史、派单记录和订单状态汇总必须处于同一事务。
5. API 使用显式动作端点，不提供可写任意 `status` 的通用更新接口。
6. 先完成并测试后端纵向切片，再接 React 和小程序页面。
7. 每个阶段有退出条件；未通过时不继续叠加下一端的功能。
8. 只实现 SPEC-004 所需能力，不顺带重构 catalog、cart 等稳定模块。

### F1-3｜确认订单并生成工单

在 `internal/fulfillment` 中实现确认命令：

1. 校验管理员 Principal；
2. 读取并锁定订单；
3. 校验 `PENDING_CONFIRMATION`、请求版本和幂等键；
4. 读取全部订单项；
5. 为每项创建一张 `PENDING_DISPATCH` 工单和关联记录；
6. 写工单初始历史；
7. 将订单改为 `FULFILLING` 并写订单历史；
8. 原子提交并保存幂等响应。

工单编号应通过数据库 sequence/唯一约束保证唯一，不依赖进程内计数器。

验证：

- N 个订单项准确产生 N 张工单；
- 同一请求重放返回首次响应；
- 相同幂等键不同请求体返回 409；
- 并发确认只有一次成功且无重复工单；
- 中途任一步失败时不留下部分工单或历史。

## 8. F3｜师傅工作台与现场状态流转

验证：伪造 ID、禁用师傅、跨组织和操作他人工单均失败且不泄露资源信息。

### F3-2｜师傅列表与详情接口

- 按待接、待上门、服务中、待补充提供本人工单列表；

- 接/拒单支持幂等，所有命令使用版本。

验证：正常顺序通过，越级命令全部 409；接单与改派并发不会出现 assignee/status 分裂。

验证：小程序 TypeScript 检查通过；开发者工具内完成接单、到达、开始；师傅 A 不可见师傅 B 工单。

## 10. F5｜客户订单中心、验收与订单汇总

### F5-2｜客户验收与返工入口

- 接受：`WAITING_ACCEPTANCE → FINISHED`；
- 拒绝：原因必填，进入 `REWORK_REQUIRED`；
- 管理端提供返回原师傅或改派处理；
- 验收使用版本和幂等键；
- 写工单历史并在同一事务汇总订单。

验证：非订单客户无权验收；重复验收幂等；拒绝后订单回到 `FULFILLING`；返工再次提交可继续正常链路。

### F5-3｜订单汇总状态

每次工单状态改变后，在同一事务内按 Spec 规则重算：

- 存在履约中工单：`FULFILLING`；
- 其余工单已完成且至少一张待验收：`WAITING_ACCEPTANCE`；
- 全部完成：`COMPLETED`；
- 全部取消：`CANCELLED`。

## 14. 风险、停止条件与回退

| 风险 | 控制措施 | 停止条件 |
| --- | --- | --- |
| migration 破坏既有订单 | 先备份/基线统计，新增 migration，空库和存量库双测 | 行数、金额或关联校验不一致 |
| 确认并发重复拆单 | 行锁、唯一键、乐观锁、幂等四层保护 | 同一订单项出现多个主工单 |
| 工单和订单状态分裂 | 工单变更事务内统一重算订单 | 主表和历史不一致 |
| 接单与改派竞争 | 带 status/version 条件更新 | assignee 与状态含义冲突 |
| 媒体越权 | 上传、绑定、读取三次资源归属检查 | 客户或师傅读到无权媒体 |
| 前端先于后端契约开发 | F0 冻结 OpenAPI，按里程碑纵向接入 | 同一字段在三端含义不同 |
| 范围扩张 | 只实现 Spec 明确端点和状态 | 引入支付、报价或智能调度需求 |

代码阶段的回退以提交为单位；数据库 migration 上线前必须验证 down 脚本，但含真实履约数据后不得直接 down，改用新的向前修复 migration。
