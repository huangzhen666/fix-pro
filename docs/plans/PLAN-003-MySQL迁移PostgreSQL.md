# PLAN-003｜FixPro MySQL 迁移 PostgreSQL 实施计划

**状态：** Completed  
**版本：** V1.0  
**日期：** 2026-08-07  
**对应 Spec：** `docs/specs/SPEC-003-MySQL迁移PostgreSQL.md` V1.0  
**关联验收：** `docs/specs/SPEC-001-SKU购物车下单正向链路.md`  
**执行原则：** 数据先审计 → PostgreSQL 空库可用 → Go 方言切换 → 数据迁移演练 → 全链路验收 → 切换 → 清理 MySQL

---

## 1. 交付目标

将 FixPro Go 后端的唯一业务数据库从 MySQL 8.4 改为 PostgreSQL 18，同时保持 React 管理后台、微信小程序和 `/api/v1` 契约不变。

最终形态：

```text
React 管理后台 ─┐
                ├─ /api/v1 → Go API → PostgreSQL 18
微信小程序 ─────┘                └→ Media Storage

MySQL
→ 退出应用运行依赖
→ 旧数据经核对后只读保留或另行确认删除
```

完成时必须满足：

- PostgreSQL 空库 migration 成功；
- Go 只使用 pgx/stdlib 与 PostgreSQL；
- 分类、SKU、媒体、购物车、下单和后台查单通过；
- 幂等并发在 PostgreSQL 事务语义下正确；
- 现有数据已迁移并通过一致性报告，或有明确的可丢弃确认；
- Compose、CI、README 和 runbook 已切换；
- MySQL 旧库未被未经确认地删除。

## 2. 当前改造面

| 范围 | 当前实现 | PostgreSQL 改造 |
|---|---|---|
| Driver | `go-sql-driver/mysql` | `pgx/v5/stdlib` |
| Connection | MySQL DSN、`sql.Open("mysql")` | PostgreSQL URL、`sql.Open("pgx")` |
| Migration | golang-migrate MySQL driver | postgres driver + PostgreSQL baseline |
| Schema | InnoDB、AUTO_INCREMENT、DATETIME、JSON、BINARY | identity、TIMESTAMPTZ、JSONB、BYTEA |
| 参数 | `?` | `$1、$2...` |
| 新增 ID | `LastInsertId()` | `RETURNING id` |
| 唯一冲突 | MySQL 1062 | SQLSTATE 23505 + constraint name |
| Upsert | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT ... DO UPDATE` |
| 搜索 | 默认 collation 下 `LIKE` | `ILIKE` |
| 联表删除 | MySQL joined DELETE | PostgreSQL `DELETE ... USING` |
| 幂等事务 | 捕获 duplicate 后继续事务 | `ON CONFLICT DO NOTHING RETURNING` |

前端代码原则上零修改，只做回归验证。

## 3. 执行约束

1. 未完成数据决策前，不删除或重建 MySQL 数据。
2. 不实现 MySQL/PostgreSQL 运行时双方言开关。
3. 不双写。
4. 不引入 ORM、通用 Repository 或通用 ETL 框架。
5. PostgreSQL migration 是目标 Schema 的干净 baseline，不机械保留 MySQL 的“建表后再 ALTER”历史。
6. 每个阶段都有独立退出条件；条件未通过不得进入切换或清理阶段。
7. SQL 行为必须由真实 PostgreSQL 集成测试验证，不能只靠 mock。
8. 旧 MySQL 下线和旧数据删除是两个动作；删除数据必须单独确认。
9. 只修改数据库迁移直接涉及的后端、部署和文档，不顺带重构业务代码。

## 4. 里程碑与停止点

| 里程碑 | 结果 | 验证 | 未通过时 |
|---|---|---|---|
| PG0 数据审计 | 明确保留/重建方案和源数据基线 | 审计报告 | 停止实施 |
| PG1 Schema | PostgreSQL 空库可重复迁移 | migration 集成测试 | 不改运行 DSN |
| PG2 Go 改造 | 所有模块通过 PostgreSQL 测试 | test/vet/build | 不进入数据迁移 |
| PG3 数据迁移 | 演练数据一致 | 一致性报告 | 清空候选库后重跑 |
| PG4 全链路 | SPEC-001 与并发/性能通过 | E2E 报告 | 不切流 |
| PG5 切换 | PostgreSQL 成为唯一写库 | smoke + 监控 | 按回滚点处理 |
| PG6 清理 | MySQL 运行依赖退出 | 静态扫描 + CI | 保留兼容清理任务 |

关键路径：

```text
PG0 → PG1 → PG2 → PG3 → PG4 → PG5 → PG6
```

## 5. 工作分解

### PG0｜数据审计与契约冻结

#### PG-0.1 确认数据处理方案

任务：

- 确认 MySQL 是否包含需要保留的分类、SKU、媒体、购物车和订单；
- 选择“保留数据迁移”或“空库重建”；
- 没有明确确认时默认保留；
- 记录负责人、停写窗口和旧库观察期。

产出：`docs/migration-reports/PG-003-data-decision.md`。

验证：文档明确写出选择、理由、确认人、确认日期和旧库删除约束。

#### PG-0.2 采集 MySQL 数据基线

对每张表记录：

- 行数；
- `MIN/MAX(id)`；
- `MIN/MAX(created_at)`；
- 金额合计；
- 唯一业务键数量；
- 孤儿关联数量；
- identity/自增当前值；
- MySQL 版本和字符集/时区。

为 JSON、BYTEA 来源字段和订单快照抽取稳定样本。媒体文件只记录路径/对象 Key、大小和存在性，不复制文件内容到报告。

产出：`docs/migration-reports/PG-003-mysql-baseline.json`。

验证：基线采集命令可重复运行；同一静态源库两次结果一致。

#### PG-0.3 冻结外部契约

- 保存现有 OpenAPI 和关键响应 fixture；
- 覆盖分类、SKU 详情、公共目录、购物车、下单结果和订单详情；
- 记录现有错误码与 HTTP 状态；
- 前端 API 类型不修改。

验证：现有 Go + MySQL 基线环境执行 `npm run check` 和契约测试通过。

退出条件：数据路径已确认，MySQL 基线和 API fixture 已保存。

### PG1｜PostgreSQL 环境与 Schema

#### PG-1.1 建立候选环境

迁移期新增独立配置：

```text
deploy/compose.postgres-migration.yaml
postgres candidate: localhost:5433
database: fix_pro
user: fixpro
volume: postgres-candidate-data
```

- 使用 `postgres:18`；
- 使用 `pg_isready`；
- 不修改或挂载 MySQL volume；
- candidate 环境密码仅为本地用途；
- CI 使用 service container 或等价真实 PostgreSQL。

验证：`pg_isready` 成功；能执行 `SELECT version(), current_setting('TimeZone')`，时区为 UTC。

#### PG-1.2 编写 PostgreSQL baseline

新增：

```text
apps/server-go/db/migrations-postgres/
├─ 000001_baseline.up.sql
└─ 000001_baseline.down.sql
```

工作内容：

- 把最终表结构一次性建成 PostgreSQL 目标形态；
- identity 使用 `GENERATED BY DEFAULT AS IDENTITY`；
- 时间使用 `TIMESTAMPTZ(3)`；
- JSON 使用 `JSONB`；
- Hash/密文使用 `BYTEA`；
- 重建唯一约束和查询索引；
- 增加 `set_updated_at()` 与必要 trigger；
- 保留现有状态字符串，不引入 enum；
- 写入 organization、本地 customer 和四个分类 seed；
- seed 使用固定 ID 时同步验证 sequence。

验证：空库 `up → down → up` 成功；Schema 与 SPEC-003 类型映射逐项一致。

#### PG-1.3 改造 migration 命令

- migrate driver 切换为 postgres；
- PostgreSQL URL 可直接传入；
- `MIGRATIONS_PATH` 支持迁移期候选目录；
- migration 日志不输出密码；
- 不复制 MySQL `schema_migrations`。

验证：空库执行后 version 正确；重复执行返回 no change 且退出码成功。

#### PG-1.4 Schema 集成测试

覆盖：

- identity 显式导入和后续生成；
- UTF-8 中文；
- JSONB 结构；
- 32 字节 Hash 约束；
- UTC 毫秒时间；
- unique/check/index；
- updated_at trigger；
- seed 数量和 ID。

退出条件：PostgreSQL 18 空库 migration 和 Schema 测试全部通过。

### PG2｜Go 数据访问改造

#### PG-2.1 切换驱动与配置

修改：

- `go.mod/go.sum` 引入 `pgx/v5`；
- `internal/platform/database` 使用 `sql.Open("pgx", ...)`；
- 默认本地 DSN 改为 PostgreSQL；
- 数据库连接池和 `PingContext` 保持；
- production 校验 TLS，拒绝明文生产连接；
- app test 的无效连接改为 pgx。

迁移工具完成前，MySQL driver 只能由一次性 data-transfer command 使用，不能再被 server 引用。

验证：配置单元测试、`go mod tidy`、`go test ./...`。

#### PG-2.2 Catalog SQL

逐项改造：

- 所有占位符；
- 分类/SKU `INSERT ... RETURNING id`；
- SKU 编码 unique violation 映射；
- `LIKE` 改 `ILIKE`；
- 分页参数；
- JSONB 发布快照写入与读取；
- optimistic lock 的 RowsAffected 行为。

验证：分类 CRUD、停用保护、SKU 草稿/编辑/发布/下架、搜索和公共目录集成测试。

#### PG-2.3 Media SQL

- 媒体新增使用 `RETURNING id`；
- 公共媒体引用查询占位符改造；
- 私有媒体 owner 校验保持；
- 引用计数和 VOID 更新保持；
- 文件存储实现不因数据库迁移改写。

验证：SKU 图片、故障媒体、公共/私有读取、跨客户拒绝和关联后不可删除。

#### PG-2.4 Cart SQL

- 购物车新增使用 `RETURNING id`；
- 重复加购改为 `ON CONFLICT ... DO UPDATE ... WHERE ... RETURNING`；
- 超过 99 时必须返回校验错误；
- 故障资料覆盖事务保持；
- 所有 owner/org 条件保持。

验证：首次加购、并发重复加购、数量 99 边界、故障资料保存/覆盖/删除。

#### PG-2.5 Order 与幂等 SQL

- 幂等占位改为 `ON CONFLICT DO NOTHING RETURNING id`；
- 禁止在 unique error 后继续使用 aborted transaction；
- 客户订单和订单项使用 `RETURNING id`；
- joined delete 改为 `DELETE ... USING`；
- JSONB 幂等响应读写；
- 搜索改为 `ILIKE`；
- `READ COMMITTED` 和 `FOR UPDATE` 保持。

验证：

- 正常下单；
- 相同 Key/相同 Hash 重放；
- 相同 Key/不同 Hash 冲突；
- 并发同 Key 只生成一单；
- 事务中任一步失败后购物车和故障资料保留；
- 后台订单分页与详情正确。

#### PG-2.6 PostgreSQL 错误映射

建立最小错误识别函数：

- SQLSTATE `23505`；
- constraint name；
- serialization/deadlock/lock timeout；
- connection/context cancellation。

只映射当前业务实际需要的错误，不建立通用数据库错误框架。

验证：错误码、HTTP 状态和客户端 message 与迁移前契约一致。

退出条件：server 不再导入 MySQL driver；所有业务模块在真实 PostgreSQL 上通过。

### PG3｜数据迁移工具与演练

#### PG-3.1 实现固定表迁移命令

若 PG-0.1 选择保留数据，新增临时命令：

```text
apps/server-go/cmd/dbtransfer
MYSQL_DSN=...
POSTGRES_DSN=...
```

要求：

- 固定表、固定列、固定顺序；
- 源库只读；
- 目标库必须为空或由命令明确拒绝；
- 分批读取和写入，批次大小固定且可测试；
- PostgreSQL 使用事务和参数化 INSERT；
- JSON 按结构解析后写入 JSONB；
- MySQL DATETIME 明确按 UTC 转换；
- BYTEA 保持原始字节；
- 失败输出表名、批次和主键范围；
- 不做双写，不创建通用 ETL 抽象。

如果选择空库重建，则此任务替换为可重复 seed/fixture，并保存可丢弃确认。

验证：对缩小 fixture 数据库迁移两次；每次从空 PostgreSQL 开始并得到相同结果。

#### PG-3.2 按依赖顺序复制

顺序：

```text
organization
→ employee_account / customer / service_category / media_asset
→ service_sku / service_sku_version / service_sku_media
→ shopping_cart / shopping_cart_item / shopping_cart_item_media
→ customer_order / order_item / order_item_media
→ work_order / work_order_status_history
→ idempotency_record / outbox_event / audit_log
```

复制期间不启动 PostgreSQL candidate server 写入。

#### PG-3.3 重置 identity

- 枚举所有 identity 表；
- sequence 下一值必须大于 `MAX(id)`；
- 空表 sequence 行为单独处理；
- 每张表迁移后插入/回滚一条测试记录验证不撞 ID。

#### PG-3.4 一致性验证

生成：

```text
docs/migration-reports/PG-003-rehearsal-report.json
docs/migration-reports/PG-003-rehearsal-summary.md
```

对比：

- 行数、主键集合；
- 金额聚合；
- unique key 数量；
- JSON 结构；
- SHA-256 字节；
- UTC 时间；
- 孤儿关联；
- 媒体记录与文件存在性；
- 抽样 SKU/订单完整详情。

退出条件：演练报告无未解释差异；目标库可以清空后完整重跑。

### PG4｜契约、并发和性能验收

#### PG-4.1 静态与单元检查


验证：全部退出码为 0；格式化后无额外差异。

#### PG-4.4 并发验收

退出条件：AC-PG-01～AC-PG-09 全部通过，形成可保存验收报告。

### PG5｜最终迁移与切换

#### PG-5.1 切换前检查

- MySQL 备份成功且恢复演练通过；
- PostgreSQL candidate 从空库完成最终 rehearsal；
- migration image 和 server image 已固定；
- 数据迁移命令版本已固定；
- 停写/回滚负责人在线；
- 旧 MySQL 不删除；
- 前端无需改包或已有可回退配置。

任一项不满足则取消切换。

#### PG-5.2 停写与最终数据迁移

1. 进入维护窗口；
2. 停止 Go API 写入；
3. 记录最终 MySQL 基线；
4. 备份 MySQL；
5. 重建干净 PostgreSQL 目标库；
6. 执行 migration；
7. 执行最终数据复制；
8. 重置 identity；
9. 运行一致性报告；
10. 报告通过后才允许启动 PostgreSQL Go server。

#### PG-5.3 切换与 smoke test

- server DSN 指向 PostgreSQL；
- 执行 health/ping；
- 查询分类、SKU、购物车和后台订单；
- 创建一条带唯一标记的验证数据；
- 验证 PostgreSQL 已写入、MySQL 未新增；
- 恢复流量。

#### PG-5.4 观察

观察：

- 5xx 与业务错误率；
- p95/p99；
- PostgreSQL connection、lock wait、deadlock；
- 订单创建与幂等冲突；
- identity/unique violation；
- 数据库容量和 WAL。

MySQL 在观察期内保持只读和可恢复，不接受新业务写入。

退出条件：观察期无阻塞问题，PostgreSQL 是唯一写库。

#### PG-6.3 文档清理

## 6. 回滚点

### R0｜切换前

PostgreSQL candidate 可随时重建；MySQL 仍是唯一写库，无业务回滚动作。

### R1｜已停写、尚未开放 PostgreSQL

若 migration、复制或核对失败：

- 不开放 PostgreSQL；
- 保留失败报告；
- 恢复原 Go + MySQL 写入；
- 修复后重新安排窗口。

### R2｜已切换但 PostgreSQL 无新增业务写入

- 停止 PostgreSQL Go server；
- 恢复 MySQL DSN；
- 执行 health/smoke；
- 恢复流量。

### R3｜PostgreSQL 已产生新写入

- 禁止直接切回 MySQL继续写；
- 优先前向修复；
- 必须回滚时进入维护窗口，先处理 PostgreSQL 新增数据；
- 不使用 migration down 作为数据回滚。
