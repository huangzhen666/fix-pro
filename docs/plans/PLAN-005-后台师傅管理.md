# PLAN-005｜后台师傅管理实施计划

**状态：** Planned  
**版本：** V1.0  
**日期：** 2026-08-09  
**对应 Spec：** `docs/specs/SPEC-005-后台师傅管理.md` V1.0  
**适用工程：** `apps/server-go`、`apps/admin-web`  
**执行顺序：** 契约冻结 → 数据模型 → 工种技能 → 师傅档案 → SKU 技能 → 候选派单 → 并发与 E2E

---

## 1. 交付目标

在现有工单履约能力之上，交付一条可在 React 管理后台完成的师傅配置与派单链路：

```text
维护工种和技能
→ 新增师傅草稿
→ 配置工种和技能并启用
→ 为维修 SKU 配置建议技能
→ 工单派单时按技能与负载选择候选师傅
→ 停用师傅并保留或退回符合条件的已有预约
```

完成时必须满足：

- 师傅、工种、技能均按组织隔离；
- 师傅至少有一个有效工种及一项有效技能后才能启用；
- SKU 技能要求只用于内部派单，不暴露给客户小程序；
- 派单候选按技能匹配度和未完成工单数排序，实际派单时再次校验；
- 师傅停用后不能接受新派单，但默认仍可履约已经分配的预约工单；
- 选择“退回未开始工单”时，只退回尚未到达的工单，不自动改派已进入履约阶段的工单；
- 关键修改具备乐观锁、事务和审计历史；
- SPEC-005 的 AC-WRK-01 至 AC-WRK-10 全部通过。

## 2. 基线、假设与边界

### 2.1 当前基线

- Go 后端和 PostgreSQL 已运行，当前 migration 为 `000001_baseline`、`000002_fulfillment`；
- `employee_account` 已承载师傅账号，工单通过 `assignee_id` 关联师傅；
- 后端已有极简师傅列表、新增和状态接口，但新增后直接启用，缺少完整档案；
- React 履约调度页已能派单，但使用通用启用师傅列表；
- React 尚无师傅管理和技能管理页面；
- SKU 已有后台新增、编辑和展示链路，但尚未配置内部技能要求。

### 2.2 本计划采用的确定性决策

1. 继续使用 `employee_account` 作为师傅主档，不再新增重复的 worker 主表。
2. 新建师傅默认是 `DRAFT`，师傅编号由后端自动生成且只读，内部用户名使用该编号，密码写随机不可登录值。
3. 工种是粗粒度职业分类，技能是工种下的能力标签；首期不做熟练度和证书。
4. 业务停用仅表示“停止接受新派单”，与安全账号锁定分离。
5. 停用默认采用 `KEEP_ASSIGNMENTS`，已有预约继续由原师傅履约。
6. `RETURN_NOT_STARTED` 只处理 `PENDING_ACCEPT`、`PENDING_ARRIVAL`；到达及之后状态保持原派单。
7. SKU 未配置技能要求时，候选列表展示所有启用师傅并明确提示未配置要求。
8. 候选排序只提供人工派单辅助，本期不实现自动派单。

### 2.3 明确不做

- 微信身份绑定、师傅自主注册和师傅后台登录；
- 身份证、银行卡、实名认证、证书和熟练度；
- 服务半径、排班、请假、预约冲突和地图能力；
- 抢单、自动派单、路线优化和智能推荐；
- 评分、绩效、提成、工资和结算；
- 师傅物理删除或通用账号锁定能力；
- 将内部工种、技能直接展示给客户。

## 3. 实施原则

1. 不修改已发布 migration，只新增 `000003_worker_management.up.sql` 和对应 down migration。
2. 工种、技能和师傅规则集中在独立 Go 领域模块，不继续扩张现有 `fulfillment` 服务。
3. 每个写命令先校验管理员权限、组织归属、状态和版本，再进行事务写入。
4. 主档、关联关系、版本和历史必须原子提交。
5. 禁用和派单竞争以数据库事务内的师傅状态复核为准，不能信任前端候选结果。
6. 历史引用只失效不删除，停用工种或技能不得破坏既有师傅及工单数据。
7. 先完成后端纵向切片和真实 PostgreSQL 验证，再接 React 页面。
8. 每个阶段通过退出条件后再进入下一阶段，不顺带重构无关模块。

## 5. W0｜契约冻结与测试骨架

### W0-1｜冻结状态与行为矩阵

整理为可执行测试表：

- 师傅状态：`DRAFT`、`ACTIVE`、`DISABLED`；
- 工种和技能状态：`ACTIVE`、`DISABLED`；
- 师傅启用的资料、工种、技能条件；
- 工种、技能停用后的新配置和历史保留规则；
- `KEEP_ASSIGNMENTS`、`RETURN_NOT_STARTED` 对每个工单状态的处理；
- 师傅业务停用与安全账号锁定的职责边界；
- SKU 有技能要求和无技能要求时的候选筛选、排序规则。

验证：每条规则都能映射到 SPEC-005 的测试场景或 AC，不存在“前端自行判断”的状态规则。

### W0-2｜冻结 API 与错误契约

- ID 统一使用字符串，时间使用 RFC3339，日期使用 `YYYY-MM-DD`；
- 明确分页结构、详情结构、负载统计、历史和脱敏手机号字段；
- 写接口明确 `version`，禁用接口明确 `workOrderPolicy`；
- 固定 SPEC-005 第 10 节错误码和 HTTP 状态。

验证：OpenAPI 语法校验通过；接口、字段、枚举和错误码与 Spec 逐项核对。

### W0-3｜建立测试夹具

准备可重复创建的：

- 两个组织及管理员；
- 启用/停用工种和技能；
- 草稿、启用、停用师傅；
- 有技能要求和无技能要求的 SKU；
- 待派、待接、待上门、已到达、服务中和待验收工单。

退出条件：OpenAPI、规则矩阵和数据库测试夹具均可被后续阶段直接复用。

## 7. W2｜工种与技能字典

### W2-1｜实现 Go API

实现 SPEC-005 第 9.1 节的列表、新增、编辑和状态接口。工种编码由后端生成 `TR{yyyyMMdd}{sequence}`，技能编码由后端按 `{tradeCode}-SK{sequence}` 生成；两类编码前端均不提供输入，编辑接口不可修改编码。

- 工种名称、编码在组织内唯一；
- 技能编码在组织内唯一，名称在同一工种内唯一；
- 技能和所属工种必须属于同一组织；
- 工种下存在启用技能时禁止禁用工种；
- 停用技能保留历史绑定，但不能用于新绑定、新 SKU 配置和新派单匹配；
- 工种仅在其下没有任何技能时允许删除；存在技能时返回 `TRADE_HAS_SKILLS`，运营人员必须先删除全部技能；
- 未被师傅绑定或 SKU 技能要求引用的技能允许删除，被引用时返回 `SKILL_IN_USE`；
- 编辑和状态切换使用 `version` 乐观锁；
- 唯一冲突返回准确业务错误码，不统一映射为用户名重复。

验证：服务层表驱动测试和 PostgreSQL 集成测试覆盖正常、重复、跨组织、状态冲突和并发编辑。

### W2-2｜实现 React 技能管理页

- 增加“技能管理”菜单和路由；
- 左侧展示工种，右侧展示所选工种的技能；
- 支持关键字、状态筛选、排序、新增、编辑、启停和删除；
- 删除工种和技能均使用 React 二次确认弹窗，后端仍再次校验组织归属及引用关系；
- 禁用工种前展示启用技能阻断原因；
- 409 时提示数据已变化并刷新当前记录。

验证：页面能创建“水电工”和“暗管测漏”，完成编辑、禁用、重新启用；刷新后数据一致。

退出条件：AC-WRK-09 通过，停用项不能进入后续新配置选项。

## 8. W3｜师傅档案、启停与历史

### W3-1｜实现师傅列表、详情和保存

替换现有极简师傅接口，完成：

- 分页、关键字、状态、工种、技能筛选；
- 新增草稿或新增并启用；
- 后端自动生成 `WK{yyyyMMdd}{sequence}` 师傅编号，写入前在组织内校验唯一性；
- 前端新增和编辑表单不提供师傅编号输入框，API 请求体也不接受人工编号；
- 详情返回基本资料、工种技能、负载、最近 20 张工单和历史；
- 编辑资料、工种和技能；
- 手机号、编号唯一冲突返回独立错误；
- 用户名不暴露给页面，密码写随机不可登录值；
- 资料、关联、版本增加和历史在同一事务。

验证：AC-WRK-01、03、05、08 的后端部分通过。

### W3-2｜实现启用

启用事务重新验证：

- 姓名、手机号合法且组织内唯一；
- 至少一个启用工种；
- 至少一项启用技能且属于已选工种；
- 师傅未被逻辑删除；
- 请求版本与数据库一致。

验证：缺工种、缺技能、技能跨工种、工种或技能已停用均失败；配置完整后启用并写历史。

### W3-3｜实现业务停用

停用接口先返回或复用详情中的分状态工单计数，确认后执行：

- `KEEP_ASSIGNMENTS`：只把师傅改为 `DISABLED`，原派单全部保留；
- `RETURN_NOT_STARTED`：将 `PENDING_ACCEPT`、`PENDING_ARRIVAL` 退回 `PENDING_DISPATCH`；
- `ARRIVED`、`IN_SERVICE`、`WAITING_COMPLETION_REVIEW`、`WAITING_ACCEPTANCE` 保留原师傅；
- 退回操作写工单状态历史和派单历史；
- 停用原因、操作人和前后内容写师傅历史；
- 状态、可选退回和全部历史原子提交。

必须保留已停用师傅处理其既有派单的业务权限；本阶段不得把业务停用实现成账号锁定。

验证：AC-WRK-06、07；尤其验证“未来预约存在时停用成功”和“保留预约后仍可继续履约”。

### W3-4｜实现 React 师傅管理页

- 增加“师傅管理”菜单、列表、筛选、分页和状态操作；
- 新增/编辑支持保存草稿、保存并启用；
- 工种多选后，仅展示对应工种下的启用技能；
- 详情展示负载、最近工单和操作历史；
- 禁用弹窗按状态展示工单数量，默认选中“保留已有预约”；
- 明确提示“停用只阻止新派单，不影响保留的已有工单”；
- 乐观锁冲突后刷新详情，不覆盖他人修改。

退出条件：AC-WRK-01、02、03、05、06、08 完整通过。

## 9. W4｜SKU 建议技能配置

### W4-1｜扩展 Go Catalog 接口

- SKU 新增、编辑和详情增加 `requiredSkillIds`；
- 只允许同组织且启用的技能；
- SKU 更新、技能关系替换和 SKU 版本增加在同一事务；
- 重复技能去重或返回明确校验错误；
- 管理后台接口返回技能信息，客户小程序目录接口不返回内部技能字段。

验证：新增、替换、清空、跨组织和停用技能测试通过；事务失败不产生半更新。

### W4-2｜扩展 React SKU 编辑页

- 增加“建议工种与技能”区域；
- 先按工种分组，再多选启用技能；
- 字段可为空，并解释“未配置时将展示所有启用师傅”；
- 编辑时正确回显并随 SKU 一起保存。

退出条件：SKU 能稳定保存和读取技能要求，小程序现有 SKU 展示不受影响。

## 10. W5｜候选匹配与派单集成

### W5-1｜实现候选查询

`GET /api/v1/admin/workers/candidates?workOrderId={id}` 必须：

- 从工单追溯订单项、SKU 和建议技能；
- 仅查询同组织、`role='WORKER'`、`status='ACTIVE'` 且未删除的师傅；
- 返回工种、技能、命中技能、要求数量和未完成工单数；
- 有要求时优先全匹配，再按命中数降序、负载升序、姓名升序；
- 无要求时返回全部启用师傅并返回“未配置技能要求”标记；
- 不把已停用技能计入新的匹配结果。

关于 SPEC 中“至少命中一项”和“技能不匹配排后或不展示”的表述，本计划采用更利于人工调度的确定实现：有技能要求时返回至少命中一项的师傅；完全不匹配者不进入候选。若业务希望允许跨技能强派，另行修改 Spec，不在实现时静默放宽。

验证：AC-WRK-04、10；覆盖全匹配、部分匹配、无匹配、无要求、同分按负载及姓名排序。

### W5-2｜强化派单命令

派单和改派事务内再次校验：

- 师傅仍属于当前组织；
- 师傅仍为 `ACTIVE` 且未删除；
- SKU 有要求时至少命中一项当前启用技能；
- 工单版本和允许状态未变化。

师傅在候选查询后被停用时，直接派单必须返回 `WORKER_DISABLED`，不得只依赖前端列表。

验证：候选查询与停用并发时，停用提交后不产生新派单。

### W5-3｜改造 React 派单弹窗

- 将通用师傅列表替换为候选接口；
- 展示师傅编号、脱敏手机号、工种、命中技能和未完成工单数；
- 标识“全部匹配”“部分匹配”和“服务未配置技能要求”；
- 提交失败时保留弹窗上下文并刷新候选。

退出条件：AC-WRK-04、07、10 完整通过。

## 11. W6｜并发、权限和 E2E 验收

### W6-1｜真实 PostgreSQL 并发测试

至少覆盖：

1. 两个管理员使用同一版本编辑师傅，只有一个成功；
2. 编辑工种或技能的乐观锁冲突；
3. 启用过程中技能被另一事务停用，不能启用无效档案；
4. 停用与派单竞争，停用提交后不得出现新派单；
5. `RETURN_NOT_STARTED` 的状态、assignee、工单历史、派单历史和师傅历史原子提交；
6. `KEEP_ASSIGNMENTS` 后，已停用师傅仍能操作保留的既有工单；
7. 已停用技能不参与新候选匹配。

验证：重复运行结果稳定，不依赖 sleep 控制时序，使用事务屏障或同步点。

### W6-2｜越权与隐私测试

- 跨组织查询、编辑、启停、配置关系和派单均返回不可见或拒绝；
- 管理员写接口执行服务层权限校验；
- 手机号列表脱敏，详情按权限返回完整值；
- 日志不记录完整手机号、地址、备注和历史 JSON；
- 客户目录接口不泄露内部技能、师傅和负载数据。

### W6-3｜后台端到端验收

按固定数据完整执行：

```text
创建工种和技能
→ 创建师傅草稿
→ 配置技能并启用
```

## 14. 风险、停止条件与回滚

### 14.1 主要风险

| 风险 | 控制措施 |
| --- | --- |
| 存量 ACTIVE 师傅迁为 DRAFT 后暂无候选 | migration 前盘点并准备补录清单，本地用测试夹具恢复候选 |
| 技能模型过细导致运营难维护 | 首期只建粗粒度标签，不做熟练度、证书和规则引擎 |
| 停用被误实现成账号锁定 | 服务层拆分业务状态判断，E2E 强制验证存量工单仍可履约 |
| 停用与派单并发产生新派单 | 派单事务内复核 ACTIVE，真实 PostgreSQL 做竞争测试 |
| 技能停用破坏历史数据 | 只阻止新使用，不删除历史关联 |
| SKU 技能未配置导致无候选误解 | 返回全部启用师傅并在 UI 明确提示 |

### 14.2 停止条件

出现以下情况时停止进入下一阶段：

- migration 无法从现有 `000002` 数据无损升级；
- 同组织唯一约束或跨组织隔离不能由测试证明；
- 师傅停用会阻止其履约 `KEEP_ASSIGNMENTS` 保留的工单；
- 派单只依赖前端候选，没有事务内状态复核；
- `RETURN_NOT_STARTED` 会改动 `ARRIVED` 或之后的工单；
- 主档、关联或历史可能出现部分提交；
- Go 或 React 当前质量门禁未恢复为绿色。

### 14.3 回滚策略

- 每个阶段独立提交，应用层可按阶段回退；
- migration 回滚只用于本地和未承载业务数据的环境；
- 已产生师傅、技能、历史或 SKU 关系的共享环境不执行破坏性 down migration，使用向前修复 migration；
- 候选接口异常时可临时回退 UI，但派单服务端的 ACTIVE 和组织校验不得回退；
- 不通过删除历史或清空关联解决技能状态问题。
