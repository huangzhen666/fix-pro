# PLAN-012｜Go 后端日志系统与线上问题定位实施计划

**状态：** 应用实现及本地验证完成；平台运行与发布验收待完成  
**版本：** V1.1  
**日期：** 2026-10-07  
**对应 Spec：** [SPEC-012 V1.0](../specs/SPEC-012-Go后端日志系统与线上问题定位.md)  
**适用工程：** `apps/server-go`、`apps/admin-web`、`apps/wechat-mini`、`deploy`、`docs/runbooks`  
**执行顺序：** 基线与契约 → Zap 底座 → 请求与错误关联 → 数据库/依赖/业务/任务/审计 → 前端参考号 → 集中采集 → 查询告警 → 故障验收 → 发布与交接

## 1. 交付目标

完成以下线上排障链路：

```text
客户端操作失败，复制错误参考号
→ Grafana 按环境、时间、requestId 查询
→ 找到请求结果、安全错误根因、operation/caller 和部署版本
→ 按 orgId + orderId/workOrderId 查看业务时间线
→ 对照 PostgreSQL 状态历史与审计
→ 按 Runbook 修复或回滚，确认操作恢复和告警解除
```

完成条件：

- Go API 与维护命令使用统一 Zap 日志，HTTP 和后台任务关联正确，隐私信息不进入日志。
- 5xx 不再只留下状态码，能够找到数据库、微信、媒体等操作的安全根因与代码位置。
- 前端普通请求、上传、下载和网络失败均保留诊断参考号，并区分客户端 ID 与服务端 ID。
- Alloy/Loki/Grafana 完成实际采集、检索、保留、告警和恢复验证，远程平台故障不导致业务不可用。
- SPEC-012 阶段 A+B 及 AC-01～AC-16 全部有验收结果与证据；真实部署/通知渠道未验证不能标为完成。

完整 OpenTelemetry 追踪属于后续阶段，不纳入本计划。不实现公开日志查询接口或新的后台日志页面。

## 2. 基线、约束与外部依赖

### 2.1 当前衔接位置

| 位置 | 需要实施的变更 |
| --- | --- |
| `cmd/server`、其它 `cmd/*` | 替换自有 slog 调用，统一配置、版本、初始化与退出清理 |
| `internal/platform/config` | 日志级别、格式、实例信息、慢操作阈值及大小上限 |
| `internal/platform/httpx` | 请求状态、请求 ID 校验、完成日志、Failure/Cause、响应包装、CORS |
| `internal/platform/auth`、`internal/app` | 认证身份绑定、路由/权限/资源诊断状态、任务生命周期 |
| `internal/platform/database` 及业务模块 | 数据库错误/慢操作、连接池快照、事务结果事件 |
| `internal/platform/wechat`、`internal/media` | 上游尝试结果、超时分类、媒体安全字段 |
| `internal/order`、`fulfillment`、`catalog` | Commit 后关键业务事件，订单/工单 ID 关联 |
| `internal/admin`、`authorization`、`workforce` | 审计 request_id、错误不再忽略、高风险修改与审计同事务 |
| 后台 `src/api/http.ts`、小程序 `services/request.ts` | 可复制的错误详情及 JSON/上传/下载异常处理 |
| `deploy`、Dockerfile、OpenAPI、Runbook | 版本注入、采集部署、保留、告警和排障说明 |

### 2.2 执行原则

1. 以当前工作区为基线，开始实施前记录 git status 和修改清单，保留已有未提交的客户认证等工作，不覆盖、重置或顺带清理。
2. 不改写已执行 SQL 迁移，新增编号以实施当时最新迁移为准；数据库实验使用独立测试库。
3. 保持 HTTP 成功响应、错误码、权限和业务事务规则；审计原子性收口按 SPEC 单独实现并验证，不混同为普通日志变更。
4. 每个里程碑验证后更新任务状态及证据；共享文件按依赖顺序修改，不要求多个代理并行执行。
5. 故障注入仅用于独立测试环境，不注册生产故障接口、不提交凭据和原始敏感日志。
6. 日志、仪表盘和告警在同一字段契约下交付；采样默认关闭，HTTP 统计不得将根因日志重复计数。

### 2.3 外部依赖登记

P0 记录生产部署形态、受信代理、CPU/磁盘预算、Grafana 入口、通知渠道/接收人、密钥注入方式、测试数据库和微信验证环境。

未提供真实通知或生产环境时，继续完成代码、测试栈、告警配置和模拟验证；对应真实环境验收保持待完成。不得把“配置文件已创建”写成“线上验证通过”。

## 4. P0｜冻结诊断契约和验证矩阵

- 盘点自有 slog/标准 log、所有 Failure 调用、认证链、数据库事务、任务、审计写入及客户端封装，列出需要迁移的具体操作。
- 冻结字段类型、保留字段、event/module/queryName/operation 命名表和错误分类；业务 ID 统一字符串。
- 固定根因责任：HTTP Failure 统一记录根因；依赖 attempt.completed 记录结果/耗时；任务入口记录任务根因。避免依赖、Service、Handler 三层重复写相同根因。
- 建立请求状态设计：认证子 context 与外层完成日志共享本次诊断状态，资源字段在授权后绑定；定义并发访问边界。
- 列出各高风险审计操作及业务事务边界，明确需要修改的调用签名与事务归属。
- 核对订单/工单历史表结构、索引和 migration 最大编号，制定增量迁移范围；不预先占用固定编号。
- 确定维护命令短生命周期日志的采集方式，验证任务结束后容器日志仍能被采集，不将服务白名单仅限于常驻 API。
- 保存原实现的固定负载基准与代码版本，避免实现完成后没有可比较基线。

交付：验收报告中的“基线/覆盖清单/事件表/外部依赖”章节；P0 完成前不批量替换日志调用。

## 5. P1｜统一 Zap 日志底座

拟新增 `internal/platform/logging`：初始化、上下文字段、事件规范、安全错误转换、限制与测试。按实际职责拆文件，不强制为每个功能建立新抽象层。

- 将配置映射到 SPEC 第 4.2 节全部选项，生产强制 JSON；版本/提交/实例由构建和部署注入，非法配置启动失败。
- 固定兼容版本的 Zap，提交 go.mod/go.sum；显式关闭生产预设采样，保留 ERROR 和高频事件全量输出。
- 对外提供 New/FromContext/关联字段绑定/安全错误输出能力；依赖注入 Logger，业务字段禁止覆盖保留字段。
- JSON 时间 UTC、级别小写、Caller 指向真实调用者；受控文本上限与最大事件大小可验证，截断保留关联信息。
- 为 pgx、网络、微信和未知错误制定类型化安全摘要；未经审核的 err、panic 值和对象不能直接输出。
- 替换 API、迁移及维护命令的自有日志入口；标准库服务器错误日志适配相同格式与安全规则。
- 优雅退出 Sync，启动失败先清理再退出；删除自有并行日志初始化，避免新旧字段混用。

验证：配置边界、字段类型/重复字段、Caller、采样关闭、截断、敏感异常安全转换、启动命令输出、日志器失败不触发业务 panic。

## 6. P2｜请求关联、身份和根因

- 实现请求 ID 单值/长度/字符校验，兼容后台 UUID 与现有小程序 ID；非法输入重新生成且不回显。
- 中间件入口创建诊断状态，认证层绑定可信 orgId/principal；拒绝访问前不绑定他人资源 ID。
- OPTIONS/404/405/认证拒绝/媒体等统一返回响应头并完成日志；CORS 暴露 X-Request-Id。
- 完成记录使用真实路由模板、最终状态、耗时、业务码和身份；无法匹配路由使用 UNMATCHED。
- 改造 Error.Cause/Unwrap 与 Failure：保存原始包装原因、安全记录一次根因、维持原响应契约；可预期 4xx 无无意义堆栈。
- 修复响应状态包装对重复 WriteHeader、1xx、隐式 200、Flusher/Hijacker/Unwrap 的处理；按底层能力保留接口，不假装支持不支持的流式行为。
- HTTP panic 写出前返回统一 500；写出后仅记录真实状态与 responseCommitted，不追加 JSON。
- 配置受信代理和关联访问日志，区分未到应用的代理错误；转发头不直接作为可信身份/IP。

验证：HTTP 表驱动及真实 httptest 服务器测试、流式/媒体读取、断连/取消、写出前后 panic、多身份并发与 race 测试。

## 7. P3｜数据库、依赖和后台任务

### P3-1｜数据库

- 引入 Query/Exec/Tx 计时与诊断 helper，先覆盖 SPEC 指定核心操作；将查询文本映射为受控 queryName，不包装并打印整个 SQL。
- 包括 Scan、rows.Err、Commit、Rollback 的错误；区分执行/扫描/事务耗时。约束错误只保留 SQLSTATE 和审核过的约束别名。
- 每分钟输出连接池快照及等待累计值/区间增量；绑定应用生命周期，退出停止快照。
- 注入约束、连接不可用、超时、死锁及连接池等待，验证 root cause 与 slow event 的责任边界。

### P3-2｜微信与媒体

- 微信每次实际调用输出 dependency.attempt.completed，包含 result、耗时、状态/上游码、操作和尝试次数；网络超时分类，不保存凭据 URL 或响应原文。
- 上传/下载输出允许的大小、MIME、结果及 mediaId；失败引用未授权资源时不记录资源 ID。
- 将日志中的客户端取消与依赖超时区分，测试桩只用于可重复失败验收，真实微信依赖另记结果。

### P3-3｜任务

- 将自动验收、自动收回、头像清理封装为带 context/超时/停止信号的任务入口，每次生成 jobRunId。
- 实际统计处理和失败数量，0 处理也记结束；取消/超时/panic 不写成功，panic 不终止下一轮调度。
- 子业务事件携带 SYSTEM 身份和 jobRunId；停止时等待受控结束，不能把重复部署实例导致的任务重复执行归因于日志。

退出条件：依赖分母可由尝试事件计算，任务可按 jobRunId 还原，失败日志无敏感数据，连接池快照统计口径正确。

## 8. P4｜业务事件与审计关联

- 逐项接入 SPEC 第 8.1 节全部事件：下单/幂等、订单确认/拒绝、派单/改派/收回、开始/完工/审核/验收、账号权限、SKU、媒体。
- 成功日志放在 Commit 成功之后；幂等命中记录命中事件，不冒充新的业务成功；幂等键不记录原文。
- 保持从状态到状态、组织、业务 ID、操作者和任务关联，失败路径从已有根因事件检索。
- 审计 helper 返回错误并接受实际事务执行器，高风险业务与审计共同提交/回滚；不在提交后补写一条可失败的独立审计。
- 填入 audit_log.request_id；历史表确有缺口才新增可空 request_id/job_run_id 和必要索引，保留历史 NULL，不伪造旧 ID。
- 独立测试库验证空库迁移、已有数据升级、审计故障回滚和历史查询；生产回滚不执行破坏性 Down。

退出条件：业务、审计、诊断事件能够对照；审计失败业务不提交，Commit 失败没有成功事件，数据库历史仍为事实来源。

## 9. P5｜前端错误参考号

- 后台 ApiError 补 HTTP 状态/失败类别，小程序 ApiError 补 requestId/状态；统一封装普通、上传、下载的 ID 生成和读取。
- ID 优先取服务端 JSON、其次响应头、最后客户端 ID；保持来源标记，网络失败说明为客户端参考号。
- fetch/wx.request/wx.uploadFile/wx.downloadFile 对空体、非 JSON、HTML、异常状态和断网分别处理，禁止解析异常覆盖原问题。
- 在下单/派单/登录/媒体失败处接入可展开、可复制的错误详情；信息仅含参考号、时间、操作、受控码和客户端版本。
- 覆盖后台 Blob/FormData 和小程序媒体处理；检查师傅小程序对公共 HTTP 契约的兼容，不无故扩展其产品交互范围。
- 更新 OpenAPI 的响应/请求 ID/CORS 说明与前端类型。

验证：后台类型检查与构建、小程序类型检查、受控响应桩和开发者工具验收；真机媒体/网络行为必须实测，不将 wx 桩标记为真机通过。

- 记录容器日志读取权限，使用受限访问方案；内网暴露 Loki/采集器，Grafana 认证，部署密钥不入仓库。
- 配置 Docker 轮转和 stdout 非阻塞/缓冲策略，量化缓冲耗尽后的丢失行为；生产根据峰值速率测算至少 24h 本地容量。

- 独立健康监控优先接入已有云监控/Prometheus；若现场没有，则提供最小 Prometheus 指标采集与主机/服务探测配置，监控磁盘、采集器错误和链路可用性，Grafana 作为告警入口。实现选定方案、版本和配置必须入验收报告，不能停留在“任选”。
- 链路探测产生受控请求及参考 ID，在限定延迟后验证 Loki 可查，并将结果写入独立监控数据源；没有请求和采集断流必须区分。

退出条件：正常 1000 条测试事件 ≥99% 在 60 秒内可见，采集标签正确，远程不可用不阻塞 API；独立健康数据源能识别 Loki/Alloy 故障。

## 11. P7｜查询、告警与排障交接材料

- 交付 SPEC 第 11 节全部查询与仪表盘，requestId/业务 ID 跳转安全编码；查询使用环境和时间限定范围。
- HTTP QPS/错误率/P95 仅统计完成事件；排除 OPTIONS/健康探测，媒体独立阈值；依赖失败率以实际尝试结果为分母。
- 配置 API 异常、核心操作失败、panic、依赖失败、任务异常、慢请求、采集断流和磁盘容量告警，阈值沿用 SPEC。
- 明确 No Data、查询故障、静默窗口、连续失败计数、分组/抑制与恢复通知；低流量阈值不能被全站错误率门槛吞掉。
- 实际通知渠道从部署密钥注入，做测试、故障和恢复通知；本地 webhook 接收桩结果与真实接收人结果分别登记。
- Runbook 提供实际 Compose/查询/只读 SQL 命令、故障原因类别、检查顺序、临时处置、回滚及恢复确认；覆盖 SPEC 列举的八类故障。
- 基础设施监控失效也需外部可用性检查/值守策略，说明单节点观测栈故障边界，不承诺所有组件同时宕机仍可自我告警。

退出条件：同一请求查到根因、业务和版本；真实接收渠道收到受控通知，内容带安全关联信息和 Runbook 链接。

### 12.2 自动化检查

以下为实施时执行的命令，本计划创建时不代表已经运行。分别在对应目录执行：

```bash

npm run build

# apps/wechat-mini

```

测试库 DSN 从安全环境注入，不写入报告。集成测试有默认数据库回退，运行前必须核对 DB_DSN 指向独立库，禁止省略该检查；普通 go test 中跳过的集成测试不能计作通过。

部署检查使用实际 overlay 执行 `docker compose ... config`，再启动独立栈进行运行验收。静态解析成功不等于 Alloy/Loki 配置有效；必须查看组件健康、真实事件和查询结果。

### 12.3 故障与性能演练

- 数据库：连接断开、超时、约束/死锁、Commit 失败、审计写入失败、池耗尽。
- HTTP/依赖：认证/越权、取消、流式写出后 panic、微信超时/异常码、上传下载异常。
- 任务：失败/超时/panic、无处理对象、停止/重启、连续失败告警。
- 平台：采集器重启、Loki 暂停 10 分钟、日志轮转、缓冲耗尽、隔离磁盘配额不足、保留删除、未授权访问。
- 安全：使用专用测试哨兵作为凭据/手机号/DSN/错误 Detail，检查应用输出、容器日志、Loki 和通知内容均无原文；不使用真实秘密。
- 性能：相同硬件/并发/业务组合/时长至少三轮，报告 P95、CPU、日志速率、采集延迟；目标 P95 增幅 ≤5%、CPU 增幅 ≤10%。

所有演练明确开始/结束、事件数、恢复时长、重复/丢失、根因 ID 和配置；资源压力只施加到隔离实例。关键业务回归包括客户登录/隔离、下单、派单、完工验收和媒体保护。

## 13. P9｜发布、回滚与完成定义

### 13.1 发布顺序

1. 备份已有部署配置、审计/历史结构与仪表盘，记录可回滚 API 版本；准备新增字段的向后兼容迁移。
2. 在 staging 启动观测栈及独立健康监控，确认资源预算、访问控制、保留、采集和告警渠道。
3. 应用增量数据库迁移，发布带版本信息的 Go 后端，再发布兼容旧响应的前端参考号改造。
4. 验证健康/真实业务、请求和业务关联、任务存活、错误脱敏、实际通知及容量；随后按现有流程发布生产。
5. 生产安排受控业务验证和排障演练，观察一周负载后复核阈值/容量；上线一周复核由运维计划执行，不创建本聊天自动化。

### 13.2 回滚规则

- 应用异常回滚 API/前端到上一稳定版本，保留新增可空字段及历史记录；不默认执行迁移 Down。
- 采集/仪表盘问题单独回滚配置与镜像，不停止业务服务；需要暂时关闭集中采集时保留本地轮转与磁盘监测。
- 审计事务改造异常优先回滚对应应用版本；禁止以关闭审计失败检测作为长期修复。
- 回滚后验证 API、业务事务、任务、旧格式日志检索和告警兼容；记录恢复窗口与潜在日志缺口。
