# SPEC-013｜通用服务 SKU 管理与结构化图文详情

**状态：** Draft for implementation  
**版本：** V2.1  
**日期：** 2026-10-28  
**适用工程：** `apps/server-go`、`apps/admin-web`、`apps/wechat-mini`  
**关联规格：** [SPEC-001](./SPEC-001-SKU购物车下单正向链路.md)、[SPEC-007](./SPEC-007-完工双级审核客户验收与售后争议.md)、[SPEC-009](./SPEC-009-后台用户角色与Casbin权限体系.md)

> 本规格适用于维修、保洁、清洗、安装、检测等服务。系统尚未上线，现有 SKU 可删除，当前没有订单；实施时直接重建，不保留旧字段、旧客户端或历史数据兼容。本次仅编写需求，不执行数据删除。案例价格、工时及保障条件均为测试示例，实际上架内容由运营确认。

**规格优先级：** 本文覆盖 SPEC-001 中三个服务说明文本字段、订单项对应文本快照、统一故障资料必填及固定数量限制的要求；替换为结构化服务内容、按 SKU 配置的需求资料和数量规则。其他交易、权限和履约要求继续适用。原墙面补漆方案仅保留为通用模型的验证案例。

## 1. 目标与设计原则

建立“模板驱动的简洁表单 + 固定视觉组件”的通用服务 SKU 管理体系。运营填写和确认业务内容，系统负责图标、排版、视觉层级及响应式展示。不向运营开放页面装修能力。

```text
清理旧 SKU → 选择服务模板（或通用模板）
→ 填基础信息、勾选服务项目、确认边界及售后、上传一张主图
→ 按需展开更多设置或增强内容 → 自动预览 → 核对并发布
→ 浏览 / 加购 / 按规则补充需求 → 下单 → 保存成交快照
```

用户应能理解服务对象、包含内容、价格单位、数量边界、准备事项与售后政策。运营新增同一规则范围内的服务时，不需要修改代码。

原则：

1. 分类用于组织目录，模板提供内容候选、规则初值和填写提示；页面始终使用同一固定组件骨架。禁止按名称、类目或模板 key 写业务分支。
2. 交易规则与展示分离：数量、费用、需求采集及售后是结构化规则，不能藏在图片或自由段落里；基础页只靠结构化内容和主图即可成立；额外图文内容通过固定增强区选填。
3. 不强迫保洁填写维修材料、故障、质保天数，也不强迫检测服务提供修前修后图片。
4. 单一 SKU 对应一项确定的服务及计价规则。不同规格先建立不同 SKU，本期不引入 SPU 或规格组合。
5. 本期使用固定单价乘数量，不通过扩大字段枚举暗示已经支持复杂报价。
6. 保留发布版本、草稿与线上隔离、并发控制及未来订单成交快照；不保留上线前旧数据兼容。
7. 不要求运营选择模块类型、图标、颜色、字号、卡片样式、标题样式或页面顺序。模板不能隐式发布未经确认的收费边界与保障承诺。

## 2. 范围与成功标准

### 2.1 本期包含

- 通用基础信息、销售单位与数量规则、服务范围、资源责任、交付与售后、需求采集配置。
- 固定组件呈现服务项目、场景标签、费用边界和售后；流程、准备事项、案例和问答等增强内容选填。
- 模板选择、简洁主表单、折叠的更多设置和增强内容、实时预览及发布校验。
- 小程序详情、列表摘要、购物车、结算及订单的规则一致性。
- 一次性旧 SKU 清理、新数据结构、API、seed 及测试夹具重建。

### 2.2 本期不包含

- 起步价、检测后报价、阶梯价、超量加价、增项支付、区域价格。
- 小数购买数量、排班产能、周期订阅、自动面积测量、自动故障判断。
- 任意 HTML/脚本、自由页面装修、模块搭建与页面排序、样式配置、任意图文块编辑器、用户自定义可执行表单 schema。
- 新的退款、售后、审核或现场作业系统。

按小时、面积销售属于固定单价计费，本期支持整数小时/平方米；需要半小时、0.5㎡等粒度时可定义固定服务包，以整数“份”购买，不把小数直接写入现有数量链路。需要现场测量结算或复杂报价的商品不在本期发布。

### 2.3 成功标准

同一套编辑器、API 和详情渲染器，能够完整配置并完成以下四个 SKU 的发布与下单：墙面局部补漆、按小时日常保洁、按面积开荒保洁、按台设备检测。至少一个 SKU 使用“通用模板”创建，不依赖类目专属模板。常规服务只需完成五组基础配置并上传一张主图，即可得到完整页面；不添加任何增强内容也能发布，不必逐项填写流程、案例和 FAQ。

## 3. 通用信息架构

| 层级 | 内容 | 是否必需 |
| --- | --- | --- |
| 基础身份 | 编码、分类、名称、简述、图片、状态、建议技能 | 编码自动生成；建议技能可选 |
| 销售规则 | 固定价格、单位、单份定义、数量范围/步长/合并方式、费用说明 | 必需 |
| 服务边界 | 服务对象、包含内容；可选的不包含与不适用情况 | 核心内容必需，限制按实际填写 |
| 交付约定 | 验收/交付标准、售后政策 | 必需；不等于必须提供期限质保 |
| 需求采集 | 是否收集需求文字、图片/视频，各自是否必填 | 明确配置 |
| 固定增强内容 | 场景标签、资源说明、服务参数、流程、准备事项、案例、问答 | 选填；系统确定组件和位置 |

“服务对象”可以是墙面、家庭空间、空调或设备；“交付标准”可以是修补部位确认、约定区域清洁检查、安装调试结果或检测报告。不使用“故障修复成功”作为通用完成条件。

上述是数据结构，不对应同等数量的必填文本框。模板填充框架及合理初值，运营通过勾选项目、选择政策和编辑少量参数完成配置；后台展开完整表单仅用于更复杂业务。

## 4. 销售与数量规则

### 4.1 价格与单位

- 保留 `priceMode: FIXED`、`basePrice`（整数分）、`unit`（1–8 字的非空单位）。`unit` 仅在基础字段维护，页面和快照统一读取。
- `billing.unitDefinition` 说明一单位实际对应的服务；如一处局部补漆、1 人服务 1 小时、按约定面积口径计算的 1㎡或一台设备。
- `billing.quantity` 配置最小值、最大值、步长及 `aggregation`。整数范围统一 1–9999，满足 `max >= min`、`step >= 1`；合法数量为 `min + n × step` 且不超过 max。
- `aggregation: INDEPENDENT`：每单位为独立对象/部位，增加数量不扩大单个对象边界。
- `aggregation: ADDITIVE`：数量累加同一订单项的小时、面积等服务额度；不表示自动增加人员，也不承诺连续排班。
- `quantityExplanation` 补充计量口径、人数、面积算法、超出边界如何处理等，不能覆盖结构化 min/max/step 或 aggregation。
- `visitFeeMode` 为 `INCLUDED`、`WAIVED`、`NOT_APPLICABLE`；本期不支持另行收取上门费。配合 `feeDescription` 说明套餐费用边界。

### 4.2 全链路行为

- 详情页数量初值为 min，按 step 增减，边界按钮禁用；购物车合并后仍校验数量，不静默截断至 max。
- 加购、购物车更新、直接下单、购物车结算均由服务端按成交发布版本执行数量与金额校验。购物车数量列原有1–99数据库约束及三端硬编码上限同步替换为1–9999的通用上限，再按各SKU配置收紧；不能只改页面步进器。
- 金额为 `basePrice × quantity`，仍采用整数分及现有金额上限。列表不得自行根据工时或面积文字推算另一种价格。
- 展示销售单位、单份定义、数量和小计。可按 ADDITIVE 显示累计小时/面积，但不推导人员数、到场次数或施工效果。
- 数量或服务规则发布变更后，原加购版本必须重新确认；不自动将不合法数量改成另一个值。
- 多个订单项分别保留各自规则。既有同 SKU/版本购物车合并语义继续使用；不同地址仍在既有分单链路处理，本期不新增逐单位地址表单。

## 5. 通用数据契约

### 5.1 核心对象

SKU 统一使用非空 JSONB/DTO 对象 `detailProfile`。`schemaVersion` 固定为 1；模板仅是来源标记。本次尚未实施，直接按本版本定义结构，无需为前版 SPEC 的字段提供适配。

草稿最少提交 `{ "schemaVersion": 1 }`，允许业务字段不完整；更新提交完整当前对象。保存校验字段类型、已填字段长度、枚举、媒体归属；发布执行所有条件必填校验。null、空对象、未知 schemaVersion 或未知字段拒绝。

| 字段 | 类型及发布规则 |
| --- | --- |
| `schemaVersion` | 固定 1 |
| `templateKey` | 可空字符串，最多 64 字，仅记录来源；不约束服务类型 |
| `serviceTarget` | 5–150 字，说明服务对象与基础适用范围，必填 |
| `billing.unitDefinition` | 5–120 字，单份服务定义，必填 |
| `billing.quantity` | `{ min, max, step, aggregation }`，见第 4 节，必填 |
| `billing.quantityExplanation` | 5–200 字，说明购买数量含义，必填 |
| `billing.visitFeeMode` | `INCLUDED / WAIVED / NOT_APPLICABLE`，必填 |
| `billing.feeDescription` | 5–200 字，费用说明，必填 |
| `includedItems` | 1–12 项 `{ title, description, iconKey?, imageMediaId? }`，必填 |
| `excludedItems` | 0–12 项 `{ title, description }`，可选 |
| `unsuitableConditions` | 0–8 个字符串，每项 2–100 字，可选 |
| `purchaseNotices` | 0–8 个字符串，每项 5–150 字，可选；有关键限制须在此填写 |
| `acceptanceCriteria` | 1–8 个字符串，每项 5–150 字，说明服务交付或检查标准，必填 |
| `afterSales` | 通用售后政策对象，见 5.2，必填 |
| `demandCollection` | 需求采集规则，见 5.3，必填 |
| `enhancements` | 可空的固定增强字段对象，见第 6 节；不存在任意 modules 数组、type 分发或页面排序字段 |

通用条目标题 2–30 字，说明 5–200 字。数组顺序即展示顺序，关键限制不截断。长度按去除首尾空白后的 Unicode 字符数计算；整个 detailProfile 序列化后不超过 64KiB，媒体文件不内嵌。文本纯文本渲染，不执行 HTML。

### 5.2 售后政策

`afterSales` 使用通用政策，不以 warranty 为强制核心字段：

| 字段 | 规则 |
| --- | --- |
| `type` | `WARRANTY`（期限质保）、`REWORK`（复洁/重做政策）、`SUPPORT`（结果咨询/一般售后），必填 |
| `summary` | 5–120 字，用户可直接理解的政策摘要，必填 |
| `coverage` | 5–300 字，具体保障/处理范围，必填 |
| `exclusions` | 0–8 条，每条 5–150 字，可选 |
| `period` | 可空 `{ value, unit, startDescription }`；value 为 1–3650 整数，unit 为 `HOUR / DAY / MONTH`，起算说明 5–100 字 |
| `contactDescription` | 5–150 字，如何联系和提供什么信息，必填 |

`WARRANTY` 必须有 period；`REWORK` 可设置反馈期限或不设固定期限；`SUPPORT` 可以不含 period。期限仅表达已约定的政策，不代表系统自动审批、自动派单或自动计算赔付。保洁示例使用“完工后 24 小时内反馈核查”的复洁政策，不显示“质保 24 小时”。页面根据 type 使用“质保说明 / 复洁或重做说明 / 售后支持”，不按类目切换。

### 5.3 需求采集

`demandCollection` 包含 `description` 和 `media` 两项，各自使用 `mode: HIDDEN / OPTIONAL / REQUIRED`，可见时必须提供 label（2–20 字）及 hint（5–150 字）。

- description 为需求文字，统一上限 500 字；REQUIRED 时去空白后至少 5 字。
- media 为图片/视频，复用已有安全上传流程、媒体数量/类型/大小上限；REQUIRED 时至少 1 个有效媒体，可选文字提示具体拍摄内容。
- 维修可配置“故障描述、现场照片”必填；保洁可配置“清洁需求、现场照片”选填；检测可配置“设备信息”必填、照片选填。
- 同一套结算组件按规则显示字段、标签、提示和校验；隐藏字段不向用户索取资料，不要求保洁填写无关故障。
- 从客户端、API、购物车、订单和履约读写中将 `faultDescription` 等专属命名统一替换为 `demandDescription`、`demandMedia`，相关数据库列和类型同步重建；不保留两个名称双写。
- 服务端按绑定发布版本校验，规则随 SKU 发布与成交快照冻结。需求资料属于客户输入，不写入商品配置；写入订单项自身字段和媒体关联。
- 更新草稿规则不自动删除客户已填写的资料；SKU 正式发布规则变化后按版本变化处理，用户重新确认后使用新规则校验。

## 6. 固定视觉组件与增强内容

### 6.1 基础配置直接生成的视觉

页面组件由产品和设计统一开发，运营没有组件类型或样式选择器。同一份结构化内容自动转换成以下界面：

| 数据来源 | 固定视觉组件 | 无额外素材时 |
| --- | --- | --- |
| 主图、名称、简述 | 16:10服务图、标题和简述 | 一张主图即可；不拿Logo或重复图片填充内容 |
| 价格、单位、单份定义 | 价格摘要卡、数量步进器、小计 | 直接展示真实规则，不依赖图片文字 |
| includedItems | 图标＋短标题＋说明的服务项目卡 | 系统统一线性图标，仍有完整卡片和层次 |
| 不包含、不适用、购买提示、费用 | 费用摘要与浅色边界提示卡 | 纯文字保持简短清晰，不强行加装饰图 |
| acceptanceCriteria | 交付检查清单 | 系统检查图标与逐条文本 |
| afterSales | 售后政策卡 | 按政策类型显示标题，无期限不展示天数徽标 |

服务项目使用 `includedItems` 中的可选系统 `iconKey`，模板可以预置，未指定使用通用服务图标。运营主表单不提供图标选择器，亦不接受自由图标URL。图标不决定服务规则。允许给单个服务项目选填 `imageMediaId`；有图时组件在原位置展示照片，无图时用系统图标，运营不选择卡片布局。项目图不能替代项目文字说明或收费边界。

### 6.2 固定增强字段

增强内容统一放在 `detailProfile.enhancements`。不配置时可省略或为 null，空数组等同无内容。后台只有固定栏目，既不新增同类型栏目也不调整栏目位置。

| 字段 | 结构和限制 | 系统展示 |
| --- | --- | --- |
| `tags` | 0–6个字符串，每项2–16字 | 适用场景标签，位于价格摘要之后 |
| `facts` | 0–8项 `{ label, value }`；label2–20字，value1–100字 | 两列服务参数，长内容换行 |
| `resources` | 0–8项 `{ name, provider, description }`；provider为PROVIDER/CUSTOMER/SHARED，名称2–30字，说明5–150字 | 工具/材料/现场条件责任列表；购买摘要可查看 |
| `preparations` | 0–8个字符串，每项5–150字 | 服务前准备清单 |
| `steps` | 0项或2–6项 `{ title, description, iconKey? }`，使用通用条目长度 | 固定步骤条，窄屏纵向展示 |
| `gallery` | 0–6项 `{ mediaId, caption }`，caption5–100字 | 单列或固定双列的成果/过程图片，系统适配屏宽 |
| `comparisons` | 0–3项 `{ title, beforeMediaId, afterMediaId, description, effectNotice }`；标题2–30字、说明5–200字、效果提示5–150字，两图不同 | 前后对照卡，固定标签及图片比例 |
| `faqs` | 0–6项 `{ question, answer }`；问题5–60字，回答5–300字 | 折叠问答 |

同一增强栏目内按输入顺序展示，可以编辑或删除内容，不提供拖拽/上下移动排序控件；页面栏目顺序由系统固定。用户确有复杂范围时在服务项目中按“厨房清洁”“卫生间清洁”等业务项目填写，不新增重复页面模块。

`facts` 只表达服务参数，不能替代交易规则或排班。`resources` 一旦涉及费用或客户准备，必须在主表单“服务边界”或发布摘要中可查看并确认，不允许只藏在增强区。新增任意参数不改变必填规则或价格算法。

系统图标白名单为 `service / inspect / protect / tool / clean / install / report / confirm`。增强字段及项目图片均使用现有媒体上传能力；不提供HTML、任意图文块、外部图片或脚本入口。普通素材说明用图片caption，不要求运营制作详情长图。

## 7. 后台简洁表单与小程序固定页面

### 7.1 模板入口及五组基础配置

新建第一步选择“维修、日常保洁、设备检测、通用服务”等模板；没有合适模板时选择通用服务，无需等待开发新增类目模板。分类独立选择。SKU编码由服务端生成唯一值，作为只读信息显示，不要求运营手工编码；基础发布和权限语义不变。

主表单仅包含以下五组：

| 配置组 | 运营操作 | 系统承担 |
| --- | --- | --- |
| ① 服务信息 | 名称、分类、价格、销售单位 | 生成编码；固定价模式不用反复选择 |
| ② 服务内容 | 勾选模板候选项目，可改名称和说明；通用模板可直接添加项目 | 带出可编辑服务对象/简述建议及统一图标，自动排版项目卡 |
| ③ 计价与边界 | 确认“一份包含什么”、常见不包含/限制、上门费；有工具材料责任则确认 | 模板提供候选文案，不强制逐项手写，不自动推断面积或人数 |
| ④ 交付与售后 | 选择交付检查项、售后政策；按实际填期限等必要参数 | 条件显示输入框，统一政策卡；不选质保时不显示保障天数 |
| ⑤ 服务主图 | 上传一张真实或明确为示意的服务主图 | 自动裁切预览及固定比例展示，其他图均选填 |

简述、服务对象、数量说明、费用说明、交付清单、联系说明等仍是明确业务数据，但由模板提供可编辑文案或选择项，不要求为每个API字段单独填写文本框。无可靠初值的业务参数保持空白，由条件校验明确提示。不能从标题或照片自动生成未经确认的承诺。

主表单显示实时手机预览，并提供“更多设置”“增强内容”两个折叠入口。必需事项始终可见；更多设置中若有未完成的必填项，在入口和发布摘要上明确标记，不能静默隐藏错误。

### 7.2 更多设置

- 数量最小/最大值、步长、独立对象或累计额度，以及需求文字/媒体是否必填，移到更多设置。
- 新建先物化模板建议值；通用模板默认数量min=1/max=99/step=1、独立对象，需求文字与媒体均选填，使用通用标签。只提供保守的技术初值，不表示适合每种服务。
- 小时/面积等模板可建议累计额度及相应下限，但按显式数据规则执行，禁止按单位字符串自动改变价格算法。
- 选择销售单位后，主表单同步展示“每份含义”和数量摘要供核对；运营不展开更多设置也能看到实际生效规则。模板默认数量错误时可以在更多设置修改。
- 需求资料默认规则在发布摘要中可见，维修或检测模板的必填建议仍需确认。系统将最终规则物化保存为SKU数据，不在小程序运行时套用模板默认值。
- 建议技能等内部配置放此处；不新增无关配置门槛。

### 7.3 增强内容与模板

增强内容仅提供第6.2节的固定栏目，以及服务项目旁的可选图片上传。默认折叠；不添加素材也不影响基础页完成度。无需运营理解GALLERY/COMPARISON等技术枚举，也不提供颜色、字号、卡片、模块类型和排序入口。

首期内置 `GENERAL_SERVICE_V1`、`WALL_PAINT_PATCH_V1`、`HOME_CLEANING_V1`、`DEVICE_INSPECTION_V1`。模板包含候选服务项目、常见边界、流程/准备事项建议及规则初值，使用同一字段schema。新增 `GET /api/v1/admin/catalog/sku-detail-templates`，复用SKU查看权限。

- 价格、面积上限、材料责任、质保天数等不能默认成为生效承诺。无可靠值保持空白；候选项目和政策需选中或核对后才进入有效表单。
- 通用SUPPORT候选文案可以是“如对本次服务有疑问，请联系客服核查”，不预填“免费返工”“无条件退款”或未经确认的响应时效。WARRANTY/REWORK的范围和期限由运营选择/填写。
- 合理默认值与服务文案均实际存入草稿，手机预览显示当前值。发布摘要集中列出有效项目、价格、单份/数量规则、费用/资源责任、售后及资料必填项，由运营核对后发布。
- 初始化模板不直接创建已发布SKU。编辑时更换模板须显示将替换的业务内容并确认，保留身份、价格及已上传素材；不能悄悄替换有效承诺。
- 模板更新不追溯修改现有SKU或订单。templateKey仅作来源记录，不控制渲染和交易。

### 7.4 小程序固定顺序和视觉要求

```text
服务主图 → 标题/简述/价格/单份定义/数量小计
→ 场景标签（可选） → 包含服务项目卡
→ 费用/不包含/不适用/购买提示（按内容显示）
→ 服务参数/工具材料/准备事项（各自有内容才显示）
→ 服务流程（可选） → 成果图/前后对照（可选）
→ 交付检查清单 → 售后政策 → 常见问题（可选）
→ 固定底栏：客服/购物车/加入购物车/立即预约
```

- 组件顺序、字号、配色、圆角、间距和图片比例由统一设计控制。运营不能覆盖主题或删除核心价格、边界及售后。
- 主图约16:10；以375px为参考设计。主图之后紧接价格和单份摘要，不能被大型品牌图或装饰区隔开。
- 项目卡默认使用统一图标、短标题、说明；有项目照片时在相同位置增强。信息层次靠留白、字重和卡片建立，不要求给每个条目配图，也不把文本拼接成大段落。
- 费用和限制使用浅色提示卡；售后使用政策图标和摘要。颜色只作辅助，不将所有内容都渲染成相同白卡里的长文字。
- 无流程不编造默认流程，无案例不展示空轮播，无图片不拿随机图库冒充作业效果；仅一张主图的页面仍完整、有层次。
- 正文不低于14px，关键文案自然换行。FAQ可折叠，收费、重要限制和关键保障直接可见；320–430px宽度及安全区适配。
- 保洁无默认故障或施工专属文字；页面根据结构化售后类型显示政策标题，根据配置内容显示服务说明，不根据模板key切页。
- 购物车、结算与订单继续显示关键购买摘要及需求规则；客服沿用现有能力，不增加没有闭环的报价或售后按钮。

## 9. 存储、API 与重建

### 9.1 唯一事实来源

- 基础身份、basePrice、unit、封面/轮播、状态、建议技能保持基础字段；其他规则统一在 detailProfile。新建时SKU编码由服务端生成并校验唯一性，不再要求管理端提交手工编码；保存后编码不可变。
- 删除 `serviceScope`、`exclusions`、`warrantyDescription` 及对应旧数据库列和订单文本快照；不生成兼容摘要或双写。
- 当前 SKU 使用 `detail_profile`，非空 JSONB，约束为对象且 schemaVersion 为1；发布版本保存完整 snapshot_json；订单项使用非空 `detail_profile_snapshot`。
- 新订单保留基础成交字段、数量、需求文字及媒体，服务规则只读取成交快照；SKU后续修改不改写已成交订单。
- 列表 DTO 仅投影基础信息、单份定义和必要数量摘要；详情 DTO 返回完整内容。列表与详情分开定义，避免接口包含大量增强图片。
- 所有公开字段和规则来自已发布版本，草稿预览不增加绕过发布权限的公开接口。

### 9.2 统一修改入口

涉及 `SkuEditPage.tsx`、`api/catalog.ts`、小程序目录与详情、购物车和结算、两端订单展示、Go catalog/cart/order/fulfillment、媒体绑定、OpenAPI、seed 和测试夹具。实施时搜索所有旧字段和故障专属命名引用，统一替换；不得只改详情页。

需求媒体关联继续复用现有表及权限机制，按通用语义调整字段和代码名称；不强制为了命名重建所有媒体表。改变的是采集规则，不扩大现有媒体访问权限。

### 9.3 一次性清理

1. 维护窗口停止旧 SKU 写入，确认订单主表和明细为空；发现订单则失败并报告，不扩大为删除订单或履约数据。
2. 删除旧 SKU 购物车项及其媒体绑定，更新受影响购物车版本；保留客户及购物车容器。
3. 按依赖顺序删除 `service_sku_skill_requirement`、`service_sku_media`、`service_sku_version`、`service_sku` 的旧数据。
4. 保留分类、技能、账号、地址、权限、媒体实体及存储文件；仅删除本次明确的业务绑定。
5. 用一次性新增迁移完成清理与结构变更，事务失败整体回滚；不改已执行 baseline，不使用整库 TRUNCATE CASCADE，不在每次启动清空。
6. 更新旧 seed/初始化脚本和客户端目录、购物车缓存；旧 ID 返回不存在，不按名称映射新商品。
7. 新库完整迁移链与新模型 seed 均可运行；四个示例可在测试环境幂等初始化为草稿，不复用旧 ID、不自动上架。

## 10. 版本、媒体和校验

- 任一客户可见规则/增强内容/条目顺序/媒体变化均参与发布版本比较；同内容重复发布去重，草稿编辑不改变当前线上内容。
- 数量、内容或需求采集规则变化，购物车和立即下单均要求重新确认版本；服务端统一执行新版规则，不静默接受旧约定。
- 订单基础字段、结构化成交快照和客户需求资料同事务写入，失败不得产生缺失承诺的订单。
- 图片包括主图、服务项目图及案例图片均检查同组织、用途、上传完成、媒体类型；复用 SKU_IMAGE，不接受任意外链。
- 被发布版本或成交订单引用的媒体不能因后续草稿删除而物理删除；快照保存媒体ID及绑定，不保存短期签名URL作永久地址。
- 按固定字段结构、字段大小、条目数量、必填条件、数量规则及总请求大小校验。不假称系统能判断自由文本承诺是否相互矛盾；发布摘要由运营核对。
- 错误复用现有 envelope/requestId，并返回字段路径；新增 `SKU_DETAIL_PROFILE_REQUIRED`、`SKU_DETAIL_PROFILE_INVALID`、`SKU_DETAIL_SCHEMA_NOT_SUPPORTED`、`SKU_DETAIL_MEDIA_INVALID`、`SKU_QUANTITY_INVALID`、`ORDER_DEMAND_REQUIRED`。各错误分别定位核心配置、增强内容、数量或需求表单。
- 维持现有客户订单隔离、后台角色权限和并发更新控制，不因通用化开放其他客户需求资料。

## 11. 验收场景

### A. 简洁配置与通用性

- **A1 最少配置**：运营选模板，只完成五组基础配置并上传一张主图，不展开增强内容、不配置样式或页面顺序，即可发布完整页面；模板有效值进入预览及发布摘要。
- **A2 通用服务**：使用通用模板创建按面积保洁，四个示例走同一接口、简洁表单和固定视觉组件，不增加专属组件或templateKey业务分支。
- **A3 条件必填**：保洁无资源/案例、选REWORK且不设期限时仍可发布；WARRANTY无period不能发布，SUPPORT不要求天数。必填参数不藏在折叠区而无提示。
- **A4 无装修配置**：后台和API均无modules、自由类型、标题样式、颜色或页面排序字段；只有固定增强栏目。添加成果图及FAQ后自动出现在固定位置，删除后不留空卡。
- **A5 模板隔离**：更换模板可查看替换范围并取消，模板更新不改变现有SKU，未保存预览不改变公开目录。
- **A6 发布核对**：未经填写的价格、面积或质保数值不以示例值发布；模板默认数量和资料规则均可核对，修改更多设置会同步摘要及预览。
- **A7 草稿与并发**：合法不完整草稿可保存但不能发布；绕过前端校验同样失败，较旧并发版本不能覆盖新草稿。

### B. 数量与需求

- **B1 数量**：四个示例金额符合第8节；详情、加购、购物车合并、结算都校验min/max/step。额外构造min=2/max=8/step=2，数量3拒绝、数量4通过。
- **B2 合并语义**：补漆不扩大单处面积；保洁可累计小时但不推导人员/到场次数；改单位不改变结构化规则。
- **B3 资料规则**：保洁不上传图片可下单；补漆缺图片不能下单；文字OPTIONAL/HIDDEN不按故障描述必填，REQUIRED按配置校验。混合购物车逐项检查。
- **B4 版本变化**：发布变更数量范围、资源责任或需求必填规则，即使价格不变，旧购物车及立即下单也需重新确认。
- **B5 订单快照**：发布V2后，V1成交订单仍显示其原数量、范围、交付标准、售后及资料规则；不读取当前SKU替代。

### C. 视觉与素材

- **C1 页面**：320/375/430px无横向溢出、遮挡；主图不会挤压所有价格信息，底栏处理安全区。
- **C2 文案**：保洁无默认“故障”“施工”“质保天数”，检测不默认出现修复承诺；栏目标题由统一组件提供，关键限制默认展开。
- **C3 素材**：单张成果图可发布，前后对照必须两图有效；越权/未完成/非法媒体均拒绝，无增强内容不留空卡。
- **C4 安全**：HTML为纯文本，图片失效有占位，既有发布或成交素材保持可读，越权订单和媒体访问被拒绝。
- **C5 基础视觉**：四个示例分别仅保留一张主图、无项目照片、无增强内容，均显示图标项目卡、费用边界、交付及售后层次；不是三个长段落连续堆叠，不要求补图才能达到完成标准。
- **C6 图文增强**：给项目添加照片或补充案例后，系统自动使用预设组件，运营不改布局。移除增强图片后回到图标方案，不发生卡片重叠、空占位或页面断层。

### D. 清理与重建

- **D1 清理范围**：旧SKU和关联测试记录移除，客户、分类、技能、权限与文件保留；发现订单时不清理。
- **D2 事务**：模拟清理中途失败回滚；订单快照或需求媒体绑定失败时订单整体回滚。
- **D3 无兼容残留**：API、DTO及运行时schema无旧文本字段和故障专属请求字段；无兼容摘要、双写或纯文本回退。
- **D4 初始化**：新库完整迁移可运行，示例草稿初始化幂等，不自动发布，服务重启不清空新SKU。
- **D5 失效引用**：旧ID返回不存在，刷新购物车后无旧商品，不把旧数量转移至新SKU。

## 12. 交付顺序与完成定义

1. 通用业务字段、固定增强内容DTO、模板契约、OpenAPI、清理和结构迁移、测试seed。
2. 服务端数量/需求/发布校验，发布快照及新订单快照。
3. 后台五组简洁配置、更多设置、增强内容、模板及预览。
