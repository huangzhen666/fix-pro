# SPEC-015｜客户小程序下单页显示与交互优化

**状态：** 代码及本地自动化验证完成；完整模拟器布局与真机验收待完成  
**版本：** V1.2  
**日期：** 2026-11-08  
**适用工程：** `apps/wechat-mini`、`apps/server-go`；后台和师傅端仅同步必要的需求展示  
**目标页面：** `miniprogram/pages/checkout/index`（确认订单）、`pages/orders/detail`（订单详情及补充需求）  
**关联文档：** [SPEC-001](./SPEC-001-SKU购物车下单正向链路.md)、[SPEC-011](./SPEC-011-客户小程序微信登录与用户数据隔离.md)、[SPEC-013](./SPEC-013-通用服务SKU管理与结构化图文详情.md)、[PLAN-014](../plans/PLAN-014-客户小程序深蓝视觉与首页优化.md)

> 本规格依据本会话提出的下单页优化方案编写，定义目标界面、交互及验收要求，不代表功能已经实现。实施与验证结果见 [PLAN-015 执行记录](../test-reports/PLAN-015-checkout-demand.md)。

## 1. 目标与范围

唯一主目标是让用户用尽可能少的操作完成下单。结算只突出地址、白天上门时间、服务摘要及总价；用户无需再次阅读服务说明与须知，也无需填写备注或上传资料。已有默认地址时，用户只需选择时间、核对关键信息并提交。备注和现场资料可在下单前选填，也可在下单后更新或补充。

本期包含：简洁结算布局、移除结算页服务说明与须知入口、白天预约时段、单一选填备注入口、订单创建后的备注及资料维护、必要的加载与错误状态。

为支持下单后更新备注，允许补充必要的订单需求读写接口、并发控制与变更记录；不能仅改前端或回写已经删除的购物车数据。白天时段限制须前后端一致。不新增价格规则、优惠券、额外收费、客服入口、服务承诺或支付能力。保留现有登录保护、订单创建及支付跳转契约。结算页不增加数量修改功能；用户返回来源页调整数量。

## 2. 当前问题与目标布局

当前服务信息位于上门信息之前；每项服务默认展开备注输入框及上传区；名称、数量及小计挤在一行；附件以名称列表展示；“上门信息”“客户预约时间段”“上门时间”等标题重复。

目标结构如下，不增加大幅宣传区、步骤横幅或固定顶部标题区：

```text
原生导航：确认订单
┌ 服务地址卡 ────────────────────┐
│ 具体地址与楼号门牌              › │
│ 汉川市 · 联系人 · 手机号           │
├ 预约上门时间 ──────────────────┤
│ 请选择日期和时间段              › │
└───────────────────────────────┘
┌ 服务清单 ──────────────────────┐
│ 缩略图  服务名称                  │
│         ¥单价/单位 × 数量   ¥小计  │
│ ……其他已选服务                   │
├───────────────────────────────┤
│ 订单备注    选填，可下单后补充    › │
└───────────────────────────────┘
固定底栏：合计 ¥0.00     [提交订单]
```

## 3. 视觉与布局约束

| 项目 | 目标规则 |
| --- | --- |
| 配色 | 复用 `styles/theme.wxss`：浅灰页面、白色卡片、深蓝操作色、现有价格色；禁止新增大面积暖色底或渐变 |
| 页面间距 | 左右 16px，卡片间距 12px，卡片内边距 14–16px，圆角复用 `--radius-card` |
| 字号 | 区域标题 16px/600，服务名称与地址 14–15px/500，辅助信息 12–13px/400，底部金额 20px/600 |
| 服务缩略图 | 56×56px，圆角 8px，等比裁切；加载失败显示中性占位图 |
| 选择行 | 最小高度 44px；整行可点击，右侧箭头与内容对齐 |
| 文本溢出 | 地址完整换行；服务名称最多两行；数量、小计不相互覆盖；不通过隐藏金额解决溢出 |
| 底部栏 | 提交按钮高 44px，宽约 136–140px，沿用深蓝圆角；按钮及金额不换行 |
| 底部留白 | 预留实际底栏高度、安全区和约 12px 内容间距，不能堆叠多层空白或遮挡最后一项 |

以逻辑像素为准；在 320px、375px、430px 宽度下适配。不得设置整页固定高度或依赖固定服务数量；放大字体时内容可增高换行。公共组件修改须评估服务详情、购物车和订单详情的影响。

## 4. 各区域交互

### 4.1 服务地址

- 地址与时间位于首张卡片；不再使用嵌套边框套卡片。
- 已选地址以具体地址、楼号/门牌为主信息；城市、联系人和手机号作为辅助信息。手机号完整展示，供用户核对实际服务联系人。
- 城市沿用地址管理中保存的“汉川市”，不增加城市自由输入或跨城市选择。
- 无地址时显示“添加服务地址”，辅助文字为“请先填写上门服务地址”；整行进入现有地址选择页。
- 默认地址选择逻辑沿用现有行为；本次手动选择地址后，不被默认地址覆盖。
- 从地址管理返回只更新地址及联系人，保留已选时间、补充需求、附件和展开状态；取消地址选择保留原值。

### 4.2 预约上门时间

- 区域标题只出现一次，统一为“预约上门时间”；未选择时显示“请选择日期和时间段”。
- 已选值使用清晰的日期及时间段，例如“11月09日（明天） 08:00–10:00”；窄屏可分两行展示。
- 弹层目标高度为屏幕的 60%–65%，最大不超过 75%；左右保留日期和时间段独立滚动，不压缩底部按钮。
- 日期范围沿用当前未来 30 天、从明天开始。仅提供白天五个两小时时段：08:00–10:00、10:00–12:00、12:00–14:00、14:00–16:00、16:00–18:00。
- 移除 18:00–20:00、20:00–22:00，不展示“晚上”分组。晚间属于加班时间，本期不提供晚间预约、加班入口或加班收费能力。
- 服务端同样拒绝晚间时段，派单及改约统一采用白天时段。项目未上线，按 PLAN-015 清空现有订单及履约数据，不保留旧订单、旧晚间时段或旧客户端的兼容逻辑。
- 日期和时间选中态使用浅蓝底、深蓝字及勾选标识，不能只靠文字颜色区分。
- 首次打开可定位到明天，但时间段必须由用户选择；未完整选择不能确认，提示“请选择预约日期和时间段”。
- 点击“确认时间”才写回主页面；取消、关闭或点击遮罩放弃本次修改。再次打开定位到已确认值。
- 保留说明“师傅会联系您，确认最终上门时间”。不能将选择的时段描述为已经保证的到达时间。

### 4.3 服务清单

- 仅展示本次结算的服务，标题统一为“服务清单”。
- 每项上部为图文摘要：服务主图、名称、单价/单位、数量及该项小计。多项服务使用细分隔线，避免反复嵌套大卡片。
- 所有金额以整数分计算，展示时统一保留两位小数；小计和合计以现有接口及订单规则为准。
- 图片相对路径使用现有 `mediaUrl` 等统一处理，绝对 URL 不重复拼接 API 地址。图片异常不阻止下单。
- 结算页移除服务说明、服务须知全文及“查看服务说明与须知／查看完整服务约定”入口，不设置折叠内容、阅读勾选或重复确认弹窗。服务详情仍可在购买前查看这些信息，订单中的服务内容快照继续保留。
- 首次进入无需操作任何服务清单行，不用手动展开即可核对名称、数量和金额。

### 4.4 下单前备注：只有一个选填入口

- 服务清单末尾只显示一行“订单备注”，辅助文字“选填，可下单后补充”；不在每项服务下重复展示备注、字数、上传按钮或其他编辑入口。
- 不填写任何备注、不上传任何资料也能提交订单；不得增加弹窗追问“是否需要补充”。
- 点击后进入轻量编辑弹层，包含备注和现场图片/视频，底部只有“保存”；关闭时保留本次结算内的输入，上传失败和保存状态须明确。
- 单项服务直接编辑该项；多项服务只在用户主动打开备注编辑器后展示各项名称及对应输入，保持需求与服务的原有归属，不新增含义不清的订单级字段，也不把同一段文字自动复制给所有服务。
- 未填写时显示“选填，可下单后补充”；已有内容时统一显示“已填写”，点击可编辑。购物车带入的已有需求计入此状态，不要求重新填写。
- 备注最多 500 字，输入框初始约 72px；字数和附件状态只在编辑器中显示。图片/视频用小缩略图展示，支持预览、移除及继续添加，复用现有文件限制与授权读取。
- 从地址页返回、关闭编辑器后仍保留当前输入；上传结果按服务稳定 ID 回写。失败资源不作为有效附件，不把取消选取提示为系统故障。
- 本期不提供上传过程中后台继续提交的能力；仅用户主动上传时临时阻止提交，明确显示“资料上传中”。

### 4.5 下单后更新与补充

- 订单详情提供一个“补充／修改备注”入口，未填写时提示“可补充现场情况或图片”；已有内容显示简短摘要及附件数量。入口置于服务信息附近，不遮挡支付、订单状态或主要操作。
- 订单创建后即可操作，包括待支付、待确认、待派单、已派单及服务中；不强制先支付、等待派单或先联系人工。订单已完成、已取消或已关闭时只读，隐藏编辑入口；不能通过售后流程重新开放原需求编辑。
- 支持修改备注文字、增加现场图片/视频、移除当前资料列表中的附件；继续按订单服务项归属。复用下单前同一编辑器，不另设复杂流程。
- 编辑器回显服务器保存的最新数据；点击保存后真正持久化，再更新详情。刷新、退出重进及换设备后可读取，不能只保存在本地或购物车。
- 保存失败保留输入并允许重试，不误报成功；保存中阻止重复操作。上传成功但需求未保存时，不将附件计为已关联到订单。
- 服务端检查客户身份、订单归属、服务项归属、媒体归属、媒体用途和可编辑状态；不能修改他人订单，也不能用本人的媒体向他人的订单写入。
- 更新文字与附件关联须原子提交，并使用需求版本或等效机制避免并发覆盖。若其他设备已修改，提示刷新后核对，保留本地未保存输入；订单在编辑中结束时拒绝保存并解释原因。
- 更新只改变客户需求及附件，不修改已成交的服务内容快照、数量、价格、地址、预约时间、支付状态或订单履约状态。
- 后台和已派单师傅在重新打开／刷新订单或工单时能读取最新需求及资料；不能仅让客户端显示更新。既有工单快照不能导致后续补充信息不可见。
- 保留需求变更前后内容、附件引用、操作人及时间，供追溯。用户移除附件是从当前需求中移除，不直接物理删除历史订单及审核证据仍引用的文件。
- 本期不增加即时聊天、推送通知或师傅确认按钮，不将“保存成功”表述为“师傅已查看”。

## 5. 底部合计与提交

- 固定底栏左侧显示“合计”和真实总金额，右侧显示“提交订单”；不新增未实际计算的费用明细或优惠。
- 地址和时间未完整填写时，按钮仍允许触发校验，定位第一个缺失区域并在该区域显示中文提示；不只弹出笼统的“信息不完整”。用户修正后消除对应提示。
- 联系人、手机号和地址沿用现有接口校验规则；地址数据异常时引导用户修改地址，不新增平行联系人输入表单。
- 仅在页面未就绪、上传中或订单提交中禁用提交，避免用户不明白为何无法操作。提交时显示“正在提交…”并阻止连续点击。
- 创建失败保留全部输入，展示可理解的错误原因；恢复提交后允许重试。保留现有幂等请求机制，不因按钮重绘产生并发订单。
- 创建成功沿用当前跳转 `/pages/orders/detail?id=…&pay=1`，由订单详情承接已有支付流程；本页不展示“支付成功”或“预约成功”等未经服务端确认的结果。

## 6. 数据及状态边界

| 场景 | 必须达到的行为 |
| --- | --- |
| 立即下单 | 仅当前服务及选定数量进入结算；需求随 `directItem` 提交，不合并或修改已有购物车 |
| 购物车勾选结算 | 仅所选项目进入结算并逐项保留需求；不纳入未勾选服务 |
| 初始加载 | 显示简洁加载态，完成后再展示真实服务与金额；不能把初始 `0.00` 误呈现为有效总价 |
| 初始加载失败 | 显示失败及重试入口，不出现可提交的空订单；重试不跳过版本或可用性检查 |
| 无可结算服务 | 清晰提示并返回购物车或来源页，不保留可提交底栏 |
| 服务下架或版本变化 | 保留现有服务端检查与确认流程，引导返回核对，不静默替换服务、版本或价格 |
| 登录失效 | 沿用现有登录保护和用户数据隔离；不能展示其他用户的地址、需求或附件 |
| 下单前备注 | 完全选填；单一入口，不填写不阻塞；仅提交上传成功的媒体 ID |
| 下单后补充 | 使用订单服务项读写需求，持久化并同步到履约查看端；不依赖购物车仍然存在 |
| 晚间时段 | 前后端及履约流程统一拒绝晚间预约，现有订单按重置计划清空后重新造数 |

下单前草稿只要求在当前结算流程内保留，不新增关闭小程序后的草稿恢复；下单后已保存的备注及资料必须可跨会话、跨设备读取，并保持账号隔离。私有资料沿用授权访问，不能为预览公开媒体。

## 7. 实施涉及文件

- 主页面：`apps/wechat-mini/miniprogram/pages/checkout/index.wxml`、`index.wxss`、`index.ts`；订单详情及可复用的需求编辑器。
- 复用现有购物车、地址、订单、媒体及主题服务；结算页移除 `service-content` 引用，订单快照和服务详情的说明展示保留。
- 服务端订单需求查询／更新、媒体关联与变更记录；预约时段校验；后台／师傅端必要的最新需求读取适配。现有订单接口没有下单后需求更新能力，该部分属于新增功能，不得仅交付前端入口。
- 接口、变更记录存储及迁移方案在实施计划中明确，只增加实现上述需求所必需的内容，不开展通用备注平台建设。
- 优先使用页面级样式和展示数据整理，删除目标区域原有冲突的行内样式；不通过继续追加覆盖规则掩盖旧尺寸。
- 若现有媒体字段或授权能力无法满足预览，先记录具体限制并调整实现方案，不把未实现入口作为交付。

## 8. 验收标准

1. 信息顺序符合“地址 → 预约时间 → 服务清单 → 合计提交”，页面没有重复预约标题、虚构收费或无效入口。
2. 结算页没有服务说明／须知内容及入口，没有每项服务重复的备注入口；只显示一个选填“订单备注”行，一项服务时页面紧凑，多项服务可正常滚动。
3. 长名称、长地址、四位数量和大金额在 320px、375px、430px 宽度下不重叠、不横向溢出；底栏按钮始终可见。
4. 有默认地址时，用户只需选时间、核对后提交；完全不填写备注、不上传资料也能下单。主动打开备注后可编辑已有内容；地址往返后文字与附件不丢失，多项服务归属正确。
5. 图片、视频、加载失败占位、上传中、失败重试和移除状态清晰；未成功上传的资料不参与订单提交。
6. 预约仅展示 08:00–18:00 的五个时段，无“晚上”分组；确认与取消符合第 4.2 节。直接请求晚间时段被服务端拒绝，原有订单及履约数据按重置计划清空，使用新建数据验收。
7. 单价、小计、合计均保留两位小数且计算结果正确；主图加载失败不影响价格及提交。
8. 缺地址或时间时能定位并提示对应区域；上传中及提交中不能重复提交，失败后输入可继续编辑。
9. 立即下单与购物车选中结算分别完成真实链路验证；创建成功后进入现有订单详情及支付流程，已有购物车不被错误合并或清空。
10. 页面到底时，最后一项内容不被底栏遮挡且无大块额外留白；在带底部安全区设备上正确展示。
11. 下单后在待支付及服务中均能修改备注、增补和移除当前附件；保存后刷新及其他设备能读取，后台及已派单师傅刷新可看到最新内容。
