# SPEC-003｜FixPro 数据库从 MySQL 迁移到 PostgreSQL

**状态：** Implemented  
**版本：** V1.0  
**日期：** 2026-08-07  
**关联文档：** `SPEC-001-SKU购物车下单正向链路.md`、`SPEC-002-Java后端迁移Go.md`  
**实施对象：** `apps/server-go`、`deploy/compose.yaml`、数据库迁移与运行手册

---

## 1. 结论

FixPro 后端数据库由 MySQL 8.4 切换为 PostgreSQL 18，Go 后端继续使用 `database/sql`，驱动改为 `github.com/jackc/pgx/v5/stdlib`。本次不引入 ORM、不重写业务模块、不修改 React 或微信小程序 API。

迁移必须同时完成：

1. PostgreSQL Schema 与 migration；
2. Go 驱动、DSN、SQL 占位符和方言改造；
3. 自增 ID、唯一冲突、JSON、二进制、时间和更新时间语义等价；
4. Catalog、Media、Cart、Order 全链路回归；
5. 根据数据决策执行“保留数据迁移”或“确认可丢弃后的空库重建”；
6. 验收后删除 MySQL 驱动、迁移脚本、Compose 服务和文档入口。

PostgreSQL 18 是当前受支持主版本，生产与 CI 应固定到最新 18.x 补丁版本，而不是固定旧补丁版本。版本依据：[PostgreSQL 版本策略](https://www.postgresql.org/support/versioning/)、[PostgreSQL 18 文档](https://www.postgresql.org/docs/18/)。

## 2. 背景与现状

当前 Go 后端已经承接：

- 分类管理；
- SKU 图片、草稿、发布与下架；
- 小程序服务目录与搜索；
- 服务端购物车；
- 故障图片/视频与故障描述；
- 幂等下单；
- 管理端订单列表与详情。

当前数据库实现存在明确的 MySQL 耦合：

- `github.com/go-sql-driver/mysql`；
- MySQL DSN 与 `sql.Open("mysql", ...)`；
- golang-migrate MySQL driver；
- `?` 参数占位符；
- `AUTO_INCREMENT`、`BIGINT UNSIGNED`；
- `DATETIME(3)` 与 `ON UPDATE CURRENT_TIMESTAMP(3)`；
- `JSON`、`BINARY`、`VARBINARY`；
- `ENGINE=InnoDB`、字符集和排序规则；
- `LastInsertId()`；
- `ON DUPLICATE KEY UPDATE`、`IF()`；
- MySQL 联表 `DELETE`；
- MySQL 错误码 `1062`。

因此本次迁移不能只替换 Compose 镜像和驱动。

## 3. 目标与非目标

### 3.1 目标

- PostgreSQL 成为唯一业务数据库；
- `/api/v1` 路径、请求、响应、错误码和鉴权方式保持不变；
- 业务 ID 继续以 JSON string 返回；
- 金额继续使用 `BIGINT` 整数分；
- 时间继续以 UTC RFC3339 对外输出；
- SKU 发布快照、购物车价格锁定、订单快照和幂等语义不变；
- 支持现有数据的可校验迁移；
- 支持 PostgreSQL 空库一键启动；
- CI 在真实 PostgreSQL 上运行 migration 和集成测试；
- 最终代码与运行配置不存在 MySQL 运行依赖。

### 3.2 非目标

- 不新增支付、履约、ToB 合同或物业项目功能；
- 不借机重构 HTTP Handler、领域模型或前端页面；
- 不引入 GORM、Ent 或其他 ORM；
- 不把 `database/sql` 全面重写为 pgx 原生接口；
- 不增加无业务需求的 PostgreSQL enum、分区表、全文搜索或逻辑复制；
- 不在本次迁移中补全所有外键或重新设计历史表；
- 不同时长期支持 MySQL 与 PostgreSQL 双方言；
- 不进行双写。

## 4. 前置决策与假设

### 4.1 数据是否必须保留

实施前必须完成一次数据决策，不允许默认丢弃：

- **存在真实客户、SKU、媒体、购物车或订单数据：** 走“保留数据迁移”；
- **全部为可重建的本地开发数据：** 经负责人明确确认后走“空库重建”。

在没有明确确认前，默认按“数据必须保留”设计和验收。

### 4.2 停机窗口

当前系统不实施双写。保留数据迁移需要短暂停写窗口：停止 Go API 写入，完成最终增量核对和导入，再切换 PostgreSQL。读取可在核对阶段按实际需要进入维护模式。

### 4.3 数据规模

迁移工具不得假设永远只有演示数据。验收至少覆盖 10 万订单、对应订单项和媒体关联的数据量级，但不提前引入分区表。

## 5. 目标技术基线

| 项目 | 目标 |
|---|---|
| PostgreSQL | 18.x，开发/CI/生产主版本一致 |
| Go 驱动 | `github.com/jackc/pgx/v5/stdlib` |
| Go 数据访问 | 保留 `database/sql` |
| Migration | `github.com/golang-migrate/migrate/v4/database/postgres` |
| DSN | `postgres://fixpro:***@localhost:5432/fix_pro?sslmode=disable`（仅本地禁用 TLS） |
| 生产 TLS | `sslmode=verify-full` 或云厂商等价强校验 |
| 时区 | 数据库存储 UTC，连接会话固定 UTC |
| 字符编码 | UTF-8 |

采用 pgx 的 `database/sql` 兼容层可以把修改限制在驱动、SQL 和错误映射，不要求重写 Service/Handler。使用方式依据：[pgx stdlib 文档](https://pkg.go.dev/github.com/jackc/pgx/v5/stdlib)。

## 6. API 与业务兼容契约

以下契约不得因数据库迁移变化：

- 统一响应仍为 `{code,message,data,requestId}`；
- ID 仍为字符串；
- 金额仍为整数分；
- 空数组、`null` 和分页字段结构不变；
- 管理端 Basic Auth 与本地客户 Bearer Token 不变；
- 分类启停、SKU 发布版本、公共目录可见性不变；
- 故障媒体权限、数量和大小限制不变；
- 同一 `Idempotency-Key` 和同一请求返回原订单；
- 同一幂等键用于不同请求返回 `ORDER_SUBMIT_DUPLICATED`；
- SKU 版本或价格变化返回 `CART_SKU_CHANGED`；
- 草稿、下架 SKU 不可从公共目录购买。

前端不得添加 `postgres` 专属适配分支。

## 7. Schema 转换规范

### 7.1 类型映射

| MySQL | PostgreSQL | 要求 |
|---|---|---|
| `BIGINT UNSIGNED AUTO_INCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 支持显式导入旧 ID；迁移后重置 sequence |
| `BIGINT UNSIGNED` | `BIGINT` + 必要的 `CHECK (value >= 0)` | 金额和 ID 不允许负数 |
| `INT` | `INTEGER` | 版本、数量、排序保持范围校验 |
| `DATETIME(3)` | `TIMESTAMPTZ(3)` | 导入时明确按 UTC 解释 |
| `JSON` | `JSONB` | 允许键顺序/空白变化，不允许语义变化 |
| `BINARY(32)` | `BYTEA` + `CHECK (octet_length(...) = 32)` | 用于 SHA-256 摘要 |
| `VARBINARY` | `BYTEA` | 密文保持原始字节 |
| `VARCHAR(n)` | `VARCHAR(n)` | 长度约束保持一致 |

### 7.2 ID 与 sequence

- 所有自动生成 ID 使用 identity；
- 应用新增数据必须使用 `INSERT ... RETURNING id`；
- 禁止继续调用 `LastInsertId()`；
- 数据导入后，对每个 identity 执行 `setval`，下一 ID 必须大于当前 `MAX(id)`；
- 对外 ID 表示不变，仍转为十进制字符串。

### 7.3 时间

- `created_at`、`updated_at`、发布、预约、SLA、过期时间统一为 `TIMESTAMPTZ(3)`；
- PostgreSQL 会话时区固定为 UTC；
- MySQL 无时区 `DATETIME` 导入时按现有系统约定 UTC 解释；
- 使用一个简单的 `set_updated_at()` trigger function，为当前带自动更新时间的表恢复 MySQL `ON UPDATE` 行为；
- API 输出继续使用 UTC RFC3339，不向前端暴露数据库时区格式。

### 7.4 JSON 与二进制

- `snapshot_json`、`response_body`、`payload_json`、`detail_json` 使用 `JSONB`；
- 迁移验收比较 JSON 结构值，不比较原始字符串空白或键顺序；
- `request_hash` 使用 `BYTEA`，必须保持 32 字节；
- 幂等请求 Hash 的生成算法仍为 SHA-256，不因数据库改变。

### 7.5 索引、唯一约束和排序

- 所有现有唯一键和业务索引必须在 PostgreSQL 中显式重建；
- constraint/index 名称应保持稳定，用于错误码映射和测试；
- MySQL 默认不区分大小写的搜索改为 PostgreSQL `ILIKE`，保证 SKU 名称、编码和订单号搜索体验不退化；
- 不引入数据库 enum；状态字段继续使用 `VARCHAR`，保持现有扩展方式；
- 本次不新增业务外键，避免把数据库切换与模型收紧混在一起。

## 8. Go SQL 改造要求

### 8.1 驱动和配置

- 删除 `go-sql-driver/mysql`；
- 引入 `pgx/v5/stdlib`；
- `sql.Open("pgx", DB_DSN)`；
- migrate driver 改为 `postgres`；
- 本地 DSN 改为 PostgreSQL URL；
- 启动时 `PingContext` 保持；
- 日志不得输出完整 DSN 或密码。

### 8.2 占位符

所有 SQL 参数由 `?` 改为 PostgreSQL `$1、$2...`。一个参数在 SQL 中重复出现时可以复用同一序号，参数顺序必须通过 Repository/集成测试覆盖。

### 8.3 新增记录

以下写入由 `Exec + LastInsertId` 改为 `QueryRow + RETURNING id`：

- 分类；
- SKU；
- 媒体；
- 购物车；
- 客户订单；
- 订单项。

### 8.4 唯一冲突

- PostgreSQL unique violation SQLSTATE 为 `23505`；
- 使用 `errors.As(err, *pgconn.PgError)`；
- SKU 编码冲突继续映射 `SKU_CODE_DUPLICATED`；
- 其他唯一约束不得一律误报为 SKU 冲突，应结合 constraint name 判断。

### 8.5 购物车 Upsert

MySQL：

```sql
ON DUPLICATE KEY UPDATE ...
```

改为 PostgreSQL：

```sql
ON CONFLICT (org_id, cart_id, sku_id, sku_version)
DO UPDATE SET quantity = shopping_cart_item.quantity + EXCLUDED.quantity
WHERE shopping_cart_item.quantity + EXCLUDED.quantity <= 99
RETURNING id, quantity
```

如果冲突分支因数量超过 99 未返回记录，继续返回现有校验错误，不允许静默截断。

### 8.6 幂等下单

PostgreSQL 中任一 SQL 错误会使当前事务进入 aborted 状态，因此不能复用“MySQL 捕获 duplicate error 后继续查询”的写法。

必须改为：

```sql
INSERT INTO idempotency_record (...)
VALUES (...)
ON CONFLICT (org_id, principal_id, idempotency_key) DO NOTHING
RETURNING id
```

- 返回 ID：当前请求取得幂等占位，继续创建订单；
- 未返回 ID：查询既有 Hash 和响应；
- Hash 不同：`ORDER_SUBMIT_DUPLICATED`；
- Hash 相同且有响应：返回原订单；
- Hash 相同但处理中：按既定冲突语义返回，不创建第二张订单；
- 并发正确性必须在真实 PostgreSQL 上测试，不使用进程锁。

### 8.7 其他方言

- `IF(condition,a,b)` 改为 `CASE WHEN ... THEN ... ELSE ... END`；
- MySQL joined delete 改为 PostgreSQL `DELETE ... USING ...`；
- `LIMIT ? OFFSET ?` 改为对应 `$n`；
- `FOR UPDATE` 保留；
- `COALESCE`、`COUNT`、`LEAST` 可继续使用；
- 搜索 `LIKE` 改为 `ILIKE`；
- 不为兼容两种数据库引入运行时 SQL 方言开关。

## 9. PostgreSQL Migration 规范

迁移并行阶段使用独立目录，避免 golang-migrate 读取错误方言：

```text
apps/server-go/db/
├─ migrations/             # 当前 MySQL，只在迁移期保留
└─ migrations-postgres/    # PostgreSQL 候选迁移
```

切换完成后：

1. `migrations-postgres` 归位为 `migrations`；
2. 删除 MySQL migration；
3. migration history 只保留 PostgreSQL 的 `schema_migrations`；
4. 不复制 MySQL 的 migration history；
5. PostgreSQL migration 从最终目标 Schema 建立干净 baseline，不机械翻译“MySQL baseline + ALTER”；
6. Down 仅用于本地空库验证，不作为生产数据回滚方法。

## 10. 数据迁移方案

### 10.1 方案 A：保留现有数据（默认）

实施顺序：

1. 盘点每张表的行数、`MIN/MAX(id)`、时间范围和孤儿关联；
2. 备份 MySQL，记录备份文件校验值并验证可恢复；
3. 启动独立 PostgreSQL，执行全新 migration；
4. 使用一次性、显式表清单的数据迁移程序按批次复制；
5. 对 JSON、二进制和时间执行类型化转换；
6. 按依赖顺序导入；
7. 重置所有 identity sequence；
8. 比较行数、主键集合、关键字段聚合和随机样本；
9. 在 PostgreSQL 候选环境执行 SPEC-001 正向链路；
10. 进入停写窗口，重新迁移最终数据或执行经过验证的增量；
11. 切换 Go DSN；
12. MySQL 保持只读观察，确认后再下线。

一次性迁移程序只负责固定表和固定列，不创建通用 ETL 框架。必须支持批量、事务、明确失败点和可重复从空 PostgreSQL 重跑。迁移期允许该命令同时依赖 MySQL 与 PostgreSQL 驱动，但生产 server 不得双驱动或双写；源/目标连接分别使用 `MYSQL_DSN` 与 `POSTGRES_DSN`。

建议导入顺序：

```text
organization
→ employee_account / customer / service_category / media_asset
→ service_sku / service_sku_version / service_sku_media
→ shopping_cart / shopping_cart_item / shopping_cart_item_media
→ customer_order / order_item / order_item_media
→ work_order / work_order_status_history
→ idempotency_record / outbox_event / audit_log
```

### 10.2 方案 B：空库重建

仅在负责人确认现有数据无保留价值后使用：

1. 保存必要的可重复 seed/fixture；
2. 启动空 PostgreSQL；
3. 执行 migration 和 seed；
4. 通过后台重新创建分类/SKU；
5. 执行 SPEC-001 全链路；
6. 删除 MySQL 本地卷前再次确认目标。

“迁移工具不好用”不能成为丢弃数据的理由。

## 11. 数据一致性验收

保留数据迁移至少验证：

- 每张表源/目标行数相同；
- 所有主键集合相同；
- 所有 identity 下一值大于 `MAX(id)`；
- 金额字段总和一致；
- 订单号、SKU 编码和幂等键唯一性一致；
- JSON 结构值一致；
- SHA-256 字节完全一致；
- UTC 时间误差不超过 1 毫秒；
- 不存在新增孤儿关联；
- 媒体数据库记录和本地/对象存储文件对应关系不变；
- 抽样订单详情的服务快照、故障描述和媒体完全一致。

验收结果必须输出可保存的报告，不能只凭页面肉眼确认。

## 12. 事务与并发要求

- 下单继续使用 `READ COMMITTED` 和购物车 `FOR UPDATE`；
- SKU 编辑继续使用版本号乐观锁；
- SKU 发布快照写入和当前版本指针更新保持同一事务；
- 故障资料覆盖保存保持同一事务；
- 幂等唯一键是多实例并发的最终保证；
- 任一 SQL 失败必须整体回滚；
- 测试 PostgreSQL deadlock、lock timeout 和 transaction-aborted 行为；
- 不增加 `sync.Mutex` 代替数据库约束。

## 16. 验收标准

### AC-PG-01｜空库可启动

PostgreSQL 18 空库执行 migration 成功，Go 服务健康检查为 `UP`。

### AC-PG-02｜Schema 等价

至少两实例或等价并发条件下，相同幂等键只产生一张订单，并可返回首次响应。

若选择方案 A，一致性报告全部通过；若选择方案 B，必须存在明确的可丢弃确认记录。

最终运行代码、go.mod、migration、Compose、CI、README 和 runbook 不包含 MySQL 运行依赖。旧 MySQL 数据删除必须另行确认。

## 17. 回滚策略

切换前：停止 PostgreSQL 候选，继续使用 MySQL。

切换后但 PostgreSQL 尚无新写入：停止 Go 写入，将 DSN 恢复到 MySQL，并核对服务健康。

PostgreSQL 已产生新业务写入后：

- 禁止直接切回 MySQL 继续写；
- 首选 PostgreSQL 前向修复；
- 如必须回滚，进入维护窗口，迁移 PostgreSQL 新增数据或恢复明确时间点的备份；
- migration `down` 不作为生产数据回滚方法。

## 18. 风险与控制

| 风险 | 控制 |
|---|---|
| 只换驱动但遗漏 SQL 方言 | 全量 SQL 清单 + 真实 PostgreSQL 集成测试 |
| PostgreSQL 事务错误后继续执行 | 幂等改用 `ON CONFLICT DO NOTHING RETURNING`，测试 aborted 语义 |
| `LastInsertId` 不可用 | 所有新增统一 `RETURNING id` |
| 搜索变为大小写敏感 | 明确使用 `ILIKE` 并补契约测试 |
| JSONB 改变原始文本 | 按 JSON 结构比较，API 只返回解析结果 |
| 时间整体偏移 8 小时 | MySQL DATETIME 按 UTC 明确导入，源/目标抽样核对 |
| identity 导入后撞 ID | 每表 `setval` 并创建后续写入测试 |
| 幂等迁移后生成重复订单 | 唯一约束 + PostgreSQL 并发测试 |
| 数据迁移漏表/漏列 | 固定表列清单、行数/主键/聚合校验报告 |
| 为双库兼容引入长期复杂度 | 只允许迁移期并行环境，不实现运行时双方言 |
| 过早删除 MySQL | 只读观察、备份恢复验证、删除前单独确认 |
